# Roadmap analysis — `specs/ROADMAP.md`

## Scope of this plan

The user asked to "analyze the roadmap". Deliverable: a structured read of
`specs/ROADMAP.md` — what's done, what's in flight, what's next, what risks
sit in the document, and where the open payloads / non-goals / rules create
real constraints. This is analysis only; nothing gets edited in the source.

## How the roadmap is shaped

`specs/ROADMAP.md` is the **ordered plan**. It is not a backlog, not a wishlist.
It opens with a strict rule: "An item is only here if the evidence for it is in
the repository today. Nothing on this list is speculative product work." Items
carry four fields — **Buys / Evidence / Blocks / Done when** — and horizons are
ordering, not dates. Status of every referenced id (S1, S2, E1, T1, T2, P1, D1,
D2a, D2b, U1, U2, U3, X1) is asserted by an entry in the "Review landed work"
section, with a commit date or a `dc0f8bb003`-style short sha for the larger
deletions.

Authority is `specs/README.md`: code wins over docs when they disagree; the
roadmap is the only place to put action items; `tsc` is forbidden in favor of
`bun run typecheck`. Adding a migration breaks
`test/database/database.test.ts`'s journal assertion and that update must land
in the same commit.

## In flight — the only remaining current-work item

### U1 — Extract the TUI package

This is the lone entry under "Finish current work". Sections 1–3 of the
extraction have landed:

- `packages/util` now owns `effect` and `xdg-basedir`.
- `@/util/*`, `@/global`, `@/flag`, `@/id` have left the TUI entirely.
- Tool `input`/`metadata` types come from `@tui/util/tool-shapes`.
- Many TUI-only modules are moved, including `lsp/language`, `provider/parse`,
  `support-docs`, `prompt-blob`, `session/primitives`, `config/features`,
  `Installation.VERSION`, the viz catalog, the TTS registry,
  `interaction/spec`, `win32`, loop/snapshot/mobile shapes (now from the
  generated SDK).
- 175 of the original 240 backend→TUI cycles are closed.
- An orphaned copy of the toast component was deleted.

Sections 1–3 took **240 → 46** `@/` imports. **Section 4 — the rest of the
move — has effectively completed for the dependency direction**: an empirical
scan of `packages/tui/src` finds zero `from "@/..."` imports, and three
services (`/tui/config`, connectors, mobile tokens) have already crossed via
the new HttpApi routes. The `packages/tui` workspace exists with `bin/`,
`src/`, `script/`, `parsers-config.ts`, `tsconfig.json`. The TUI is no longer
a subdirectory of `packages/nikcli`.

What remains, per the roadmap's own wording:

1. **The terminal calling backend services in-process** — `@/effect` (11
   callers) hitting `UserDB`, `Account`, `Profile`, `Skill`, `Connectors`,
   `Brain`, plugin install, `TuiConfig.get()`, plus twelve lazily-imported
   subsystems. Each needs an HttpApi endpoint the SDK can reach; each changes
   runtime behavior; each must be exercised against a real server because the
   encoder rejects any response it cannot validate (and a bad schema looks
   like empty data, not an error).
2. **`@/image/photon` (4 imports)** is **deliberately excluded**: it resolves
   a wasm asset path that only the compiled binary can validate.
3. **`thread.ts` / `worker.ts`** stay put — they are host files, not UI, and
   the section-3 server-start inversion already existed (`tui()` takes its
   transport and host operations as props).

**Done when**: `packages/tui` typechecks with `packages/nikcli` out of its
references; no import resolves into `packages/nikcli`; the TUI starts from the
installer binary; warm startup does not regress. Verified per step by
`bun run typecheck` (33 packages), `bun test`, and a real `--single` build +
binary run for anything the bundler touches. Baseline test failures are two:
`profile command` and `EditTool`.

## Non-goals (do not re-propose)

- Nested `/project/:projectID/session/...` URLs — directory scoping is
  middleware plus storage keys (`project.md`).
- Automatic hard-crash session recovery — S2 covers graceful only.
- Clustered session ownership — needs a placement + fencing protocol.
- A shared PubSub for the event feed — rejected in E1's spec; the win would
  be queue-slot references, not frame copies.
- Rebuilding TUI features opencode already has — the jlongster set is in.

## Open payloads (real `Schema.Unknown` is allowed only here)

From `specs/README.md`, justified in-place rather than in a side document:

- upstream passthrough (third-party bodies the server does not interpret);
- polymorphic event-sourced entries (`session_entry` / sync frames whose
  variant set grows without a contract bump);
- SSE frames (the encoded event feed);
- bodyless redirects (share short-links and similar 3xx).

Everything else gets a real schema. The measurable guardrail is:

```sh
grep -cE '^export type [A-Za-z0-9_]+ = (any|Array<any>)$' \
  packages/sdk/js/src/httpapi/generated/types.ts
```

## Working rules (from the bottom of the roadmap)

- Commit at phase boundaries, not per file.
- Every commit that changes a contract updates its spec in the same commit.
- Verify with `bun test` unit tests and `bun run typecheck` (never a bare
  `tsc`; the repo's `.bin/tsc` is the JS 5.x one).
- Do not verify with the simulation harness.
- Adding a migration breaks `test/database/database.test.ts`'s journal
  assertion — update it in the same commit.

## Risks & sharp edges I see in the document

1. **U1's remaining `@/effect` (11) callers are the highest-risk work in the
   repo right now.** Each call site changes runtime behavior; the encoder
   silently turns a bad response into empty data. The roadmap warns this
   explicitly ("looks like empty data, not an error"). Any plan to finish U1
   must include "curl the route against a real server" per move, and must
   guard `bun run typecheck` plus a `--single` build, not just `bun test`.
2. **Hard-crash recovery and clustered ownership are explicitly out of scope,
   but agents / humans tend to re-propose them.** The non-goals section is the
   defense; the spec index is the offense. Any new ask in those areas needs
   to land a placement + fencing protocol first (clustered) or provider
   dispatch + idempotency + retry budgets (crash).
3. **Project URLs are deliberately flat.** The "nested under `/project/:id`"
   shape keeps coming back. The `project.md` doc plus middleware + storage
   keys is the chosen answer; pushing it as a refactor would break every
   client.
4. **Spec hygiene.** The contract documents in `specs/v2/*` and
   `specs/storage/*` are _the_ source of truth that lets the roadmap stay
   short. If a contract drifts without a spec bump, the next reader will
   reverse-engineer a contract that already disagrees with the code. The
   rule "every contract commit updates its spec in the same commit" is what
   keeps U1's remaining moves safe.
5. **Theme migration is done but `accent.fg` vs `accent.alt` was a real
   mistake.** `v2/tui-theme-migration.md` notes callers had been treating
   `accent.fg` as the document `accent` hue; `accent.fg` is `primary`, the
   extra hue is `accent.alt`. Any TUI work that touches color needs to read
   the migration doc before adding tokens.
6. **Tool registration is overlay-stacked now.** Reload of config/plugin
   tools must not drop sdk-next runtime tools; the two-cache split in T1 is
   what enforces that. Plugin autoload still requires `NIKCLI_ALLOW_PLUGIN_AUTOLOAD=1`
   or `tool.allow` / `tool.pin` (`packages/nikcli/AGENTS.md`).
7. **Journal assertion in `test/database/database.test.ts` is intentionally
   breakable.** It's a tripwire, not a bug — every migration bumps it.

## What I would recommend doing next (not part of the plan to write — just

what the document itself argues for)

The roadmap's own "horizons are ordering, not dates" rule means U1's
remaining 11 `@/effect` callers and 12 lazy subsystems are the next work,
ordered by **dependency, then by user-visible impact**. Concretely:

1. Finish the smallest two or three remaining `@/effect` moves (the ones
   without side effects: pure reads like `TuiConfig.get()`) so the SDK
   contract gains coverage cheaply.
2. Then move the dialog-bearing services (`Connectors`, `Skill`, `Brain`,
   `Profile`, `UserDB`) one at a time, **with the matching dialog exercised
   end-to-end against a real server**, per the roadmap's own warning.
3. Then `Account` and plugin install (write paths, larger blast radius).
4. Land a final pass that confirms `packages/tui` has zero `@/` imports and
   that the warm-start number does not regress against the current baseline.
5. Update `specs/tui-package.md` to mark section 4 done in the same commit as
   the last move (spec + code, per the working rules).

Each step ends with `bun run typecheck` + `bun test` + a real `--single`
binary run, in that order, one final typecheck pass (per the user's standing
convention: low-RAM machine, typecheck once at the end of an edit set).
