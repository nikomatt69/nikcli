# Piano integrato nikcli

## Interpretazione

"Integrare tutto" viene interpretato come una roadmap unica e sequenziale che unisce sicurezza, runtime, persistenza, convergenza HTTP, manutenzione, test, CI e release, senza implementare modifiche in questa fase.

## Obiettivo architetturale

Portare nikcli a un modello coerente in cui ogni richiesta sia scoped a una `Instance`, l'autenticazione e i contratti HTTP siano unici, la sessione abbia un orchestratore sottile, SQLite sia la persistenza autorevole e ogni confine abbia test end-to-end e diagnostica osservabile.

## Fase 0 - Baseline e contratti

- Congelare la baseline di `packages/nikcli/src/index.ts`, `server/server.ts`, `session/processor.ts`, `session/llm.ts`, `session/tools.ts`, `config/config.ts`, `storage/storage.ts` e `database/`.
- Definire una matrice di ownership per sessioni, messaggi, parts, permessi, sync, plugin, MCP e workspace.
- Catalogare i percorsi Hono, Effect HttpApi, SSE, WebSocket, mobile e SDK; mantenere `check:routes` come gate.
- Definire invarianti: `Instance` obbligatoria, auth unica, errori tipizzati, flush terminale della sessione, migrazioni resumable e redazione obbligatoria.
- Aggiungere test di caratterizzazione prima dei refactor, senza cambiare comportamento.

## Fase 1 - Sicurezza e confini di esecuzione (P0)

File principali: `src/server/httpapi/auth.ts`, `src/server/identity-auth.ts`, `src/server/server.ts`, `src/server/middleware/body-limit.ts`, `src/permission/next.ts`, `src/permission/ruleset.ts`, `src/plugin/index.ts`, `src/tool/registry.ts`, `src/util/redact.ts`.

- Rendere esplicito il profilo sicuro per listener non-loopback: auth obbligatoria, audience JWT obbligatoria, warning per modalità open e validazione coerente di proxy/hostname.
- Limitare i token in query string ai soli endpoint WebSocket/mobile necessari e impedire che finiscano in log, referrer o errori.
- Centralizzare ogni serializzazione di log in `safeStringify`/`redactUrl`; aggiungere una regola o test che rilevi `JSON.stringify` nei percorsi di logging.
- Rendere visibili e auditabili `--auto`, `--yolo` e `--dangerously-skip-permissions`, mantenendo sempre attive le regole deny.
- Registrare plugin e custom tool con sorgente, versione, hash e capacità; mantenere autoload disabilitato di default e pin obbligatori per ambienti non locali.
- Applicare limiti anche ai flussi chunked e associare timeout tool a terminazione reale dei processi figli quando il tool lo consente.

Verifiche: test auth con ogni modalità e listener; test token query; test redaction su log e URL; test permission deny/auto; test plugin hash/autoload; test body limit con `Content-Length` e chunked; test timeout con processo non cooperativo.

## Fase 2 - Persistenza autorevole e migrazioni (P0/P1)

File principali: `src/database/database.ts`, `src/database/migration.ts`, `src/database/schema.ts`, `src/session/repo.ts`, `src/session/message-repo.ts`, `src/storage/storage.ts`, `src/session/*.sql`, `src/sync/`.

- Stabilire SQLite/Drizzle come source of truth per sessione, messaggi, parts, todo, permessi e sync.
- Introdurre facade di repository per impedire che i domini scelgano direttamente tra `Storage`, repository SQL e accesso raw al DB.
- Completare la migrazione del file store con checkpoint, idempotenza, conteggi source/destination, journal di stato e recovery dopo interruzione.
- Validare la coerenza tra colonne indicizzate e payload JSON ancora usati da `Session.Info`; definire aggiornamenti atomici.
- Unificare il lifecycle del DB tra singleton sincrono e `Database.Service`, evitando connessioni concorrenti non necessarie e testando cambi di `NIKCLI_DB`.
- Definire shutdown esplicito per WAL checkpoint, write queue e coalescer.

Verifiche: migration test su database vuoto, database parziale e migrazione interrotta; test idempotenza; test concorrenza; consistency checker; restart durante write e durante sessione attiva.

## Fase 3 - Session runtime e affidabilita (P1)

File principali: `src/session/processor.ts`, `src/session/llm.ts`, `src/session/tools.ts`, `src/session/message-v2.ts`, `src/session/compaction.ts`, `src/session/status.ts`, `src/session/delta-coalescer.ts`, `src/bus/`.

- Scomporre `SessionProcessor` in `StreamController`, `ToolExecutionController`, `RetryController`, `PersistenceCoordinator` e `CompletionFinalizer`.
- Ridurre i wrapper `runSession`/`runPlugin`/`runCompaction` ripetuti mediante un runtime scoped unico, mantenendo `Instance` esplicita.
- Rendere deterministico il lifecycle: start, delta, tool, retry, compaction, abort, error e completed devono avere transizioni di stato documentate.
- Garantire `flushNow` per ogni uscita terminale e scartare in modo atomico le parti di retry fallite.
- Separare normalizzazione messaggi, costruzione prompt, provider transform e stream adapter in moduli testabili.
- Rendere esplicita la consegna degli eventi Bus, inclusi errori, ordine, duplicati e backpressure.

Verifiche: test state machine; stream normale/abort/error/retry/compaction; flush su ogni exit path; duplicate event test; test provider malformato; test doom-loop e content-loop.

## Fase 4 - Configurazione e contesto

File principali: `src/config/config.ts`, `src/config/features.ts`, `src/effect/with-instance.ts`, `src/project/instance.ts`, `src/agent/`, `src/provider/`, `src/tool/registry.ts`.

- Dividere la configurazione grezza in proiezioni validate: `ServerConfig`, `ProviderConfig`, `AgentConfig`, `PermissionConfig`, `PluginConfig`, `ToolConfig`, `UIConfig`.
- Definire una sola risoluzione di precedenza e una diagnostica che mostri la provenienza di ogni valore senza esporre segreti.
- Rendere l'`Instance` l'unico contesto per directory, progetto, config, DB, plugin, provider cache e permission state.
- Eliminare progressivamente accessi globali impliciti e verificare isolamento tra due progetti nello stesso processo.

Verifiche: precedence tests; config schema tests; secret display tests; two-instance isolation; provider/tool/permission resolution matrix.

## Fase 5 - Convergenza HTTP e SDK (P1)

File principali: `src/server/server.ts`, `src/server/backend.ts`, `src/server/httpapi/`, `src/server/routes/`, `packages/sdk/js/`.

- Rendere `Effect HttpApi` il contratto canonico per le route JSON.
- Conservare Hono solo per SSE, WebSocket, HTML, mobile e compatibilita esplicitamente documentata.
- Usare un'unica funzione di auth, mapping errori, schema response e scoping workspace in entrambi i backend.
- Aggiornare la matrice di eliminazione Hono in `server/backend.ts`; migrare prima i gruppi JSON candidati e lasciare bloccati i percorsi streaming finche non esiste il backend corretto.
- Rigenerare sempre SDK e client dopo modifiche agli endpoint.

Verifiche: `bun run check:routes -- --strict`; contract tests Hono/HttpApi equivalenti; auth parity tests; SDK generation diff check; SSE/WebSocket/mobile smoke tests.

## Fase 6 - Plugin, MCP e integrazioni

File principali: `src/plugin/index.ts`, `src/mcp/`, `src/connectors/`, `src/server/routes/mobile/`, `src/remote/`, pacchetti `plugin`, `remote`, `companion`.

- Formalizzare capability e lifecycle di plugin/MCP: init, event, tool, provider, dispose, timeout e failure isolation.
- Separare plugin trusted dal semplice provider di tool; impedire che un hook fallito blocchi la sessione ma conservare errore e telemetry correlabili.
- Rendere mobile/remote esplicitamente scoped, autenticati e testati contro replay, token leakage e workspace errato.
- Testare compatibilita tra core, SDK, companion e plugin versionati.

Verifiche: plugin lifecycle/reload/dispose; MCP timeout/auth; mobile bootstrap/session streaming; remote proxy authorization; compatibility smoke tests.

## Fase 7 - Test, CI, osservabilita e release (P1/P2)

File principali: `packages/nikcli/package.json`, `test/`, `script/`, root `package.json`, configurazione CI/release.

- Rendere gate distinti e obbligatori: format, lint, typecheck, unit, integration, route strict, build e release smoke.
- Aggiungere suite e2e minima CLI -> session -> provider fake/test -> tool -> persistence -> event consumer.
- Aggiungere test per migration recovery, database concurrency, auth profiles, redaction, plugin trust, subprocess timeout e restart recovery.
- Definire metriche/log correlabili per session ID, request ID, tool call ID e migration ID senza segreti.
- Aggiungere smoke test del binario costruito e verifica che SDK generato sia aggiornato.
- Rimuovere script root fuorvianti (`random`, `hello`, test che fallisce intenzionalmente) oppure documentarli esplicitamente.
- Sincronizzare versioni e documentazione operativa.

Verifiche finali: `bun run typecheck`, `bun run lint`, `bun run format:check`, `bun run test`, `bun run test:integration`, `bun run check:routes -- --strict`, `bun run build`, `bun run test:e2e` e smoke del binario/release.

## Ordine di implementazione e criteri di completamento

1. Baseline e test di caratterizzazione.
2. Sicurezza/auth/redaction e timeout.
3. Persistenza/migrazioni e shutdown.
4. Session runtime e flush deterministico.
5. Config/Instance normalization.
6. HttpApi/SDK convergence.
7. Plugin/MCP/mobile/remote hardening.
8. CI, osservabilita, release e documentazione.

Il piano e completato solo quando ogni fase ha test verdi, nessun percorso di persistenza ambiguo per i domini migrati, route coverage strict senza gap non documentati, auth parity verificata e build/release smoke riusciti.
