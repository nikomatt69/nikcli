## Phase 1 · Critical correctness fixes (server + TUI)

These are real bugs that produce wrong state, not style issues. Do these first.

### 1.1. Per-instance state for engine maps

**Problem:** `src/loop/engine.ts:86-87` declares `live` and `inFlight` as module-level `const`s. When the server handles multiple project instances (server.ts:441 wraps the app in `withInstanceAsync({ directory, init: InstanceBootstrap })`), these maps are **shared across all projects**. A loop id `loop_aaa` in project A and the same id in project B collide.

**Fix (the "best and most logical" approach):**

The engine exports a singleton (`LoopEngine`) that exposes static methods. Instance isolation must happen _inside_ the engine. The cleanest pattern, matching `mobile/routine.ts` semantics, is:

1. Move `live` and `inFlight` into a closure created by a factory `createLoopEngineState()`.
2. Store the per-instance state object via `Instance.state(createLoopEngineState, instanceStateCleanup)`. This is the same pattern `Scheduler` uses (see `src/scheduler/index.ts:29-38`).
3. The exported `LoopEngine` becomes a thin facade that resolves the per-instance state via `Instance.state(() => …)` at the top of every public method (similar to how `Monitor.reconcile()` works in `src/monitor/manager.ts`).
4. The `dispose()` / `restore()` lifecycle is keyed to the instance — no more global state.

**Files to touch:**

- `src/loop/engine.ts` — refactor `live`, `inFlight`, `livePatches`, `restore`, `dispose`, `syncAll`, `arm`, `disarm`, `runOnce`, `patch`, `setRuntimeStatus`, `runtimeOf`, `resetRunCount` to resolve per-instance state.
- No call-site changes needed in `routes/loop.ts` (the engine API surface stays the same).
- `src/project/bootstrap.ts:122` — verify `LoopEngine.restore()` is called inside the per-instance bootstrap (it is, via `InstanceBootstrap`).

**Verification:** add a unit test that calls `LoopEngine.getRuntime("loop_aaa")` under instance A then instance B and asserts the maps are independent.

### 1.2. TOCTOU race in `runOnce`

**Problem:** `src/loop/engine.ts:262-289` has a single-flight `inFlight.has(id)` check, but between the check and the `inFlight.set(id, …)` there are several `await` points. Two concurrent `runOnce(id)` calls (e.g. server tick + manual button) can both pass the guard, both call `Manager.startRun`, and both create loop run records.

**Fix:** claim the slot synchronously **before** any await. Replace the check-then-set pattern with a `pending: { kind: "claiming" | "running" }` discriminated union set inside a synchronous IIFE:

```ts
const slot = inFlight.get(id)
if (slot) return slot
const placeholder = new Promise<void>(() => {}) // never resolves
inFlight.set(id, placeholder)
try {
  // … all the awaits, then replace with the real promise
  inFlight.set(id, realPromise)
  return realPromise
} finally {
  // cleanup only after the real promise settles
}
```

**Files to touch:** `src/loop/engine.ts:262-316`.

**Verification:** unit test — call `runOnce(id)` twice in the same tick and assert exactly one `Manager.startRun` call and one `LoopRun` record.

### 1.3. Removal-while-running leaks

**Problem:** `routes/loop.ts:323-330` (`DELETE /loop/:id`) calls `Manager.remove` (cascade-deletes run records) and `Engine.disarm` even if a run is in flight. The in-flight `executeRun` continues, writes a `LoopRun` for a deleted loop, leaks its session, and leaves a stale `Runtime` entry.

**Fix:**

- In `Engine.runOnce`, after every `await`, re-check `Manager.get(id)` and bail with `{ ok: false, error: "deleted" }` if the loop is gone.
- In the route, **await** `Engine.abort(id)` before `Manager.remove`. `abort` cancels the in-flight run by (a) setting `Runtime.status = "cancelling"`, (b) calling `SessionPrompt.abort(sessionID)`, (c) awaiting the in-flight promise or timing out at 5s, (d) clearing the slot.
- After `abort` returns, `Manager.remove` is safe.
- The bus `LoopEvent.Removed` is published _after_ the abort + remove complete, so subscribers see consistent state.

**Files to touch:**

- `src/loop/engine.ts` — add `abort(id)` and the in-run re-check.
- `src/server/routes/loop.ts:323-330` — call `Engine.abort` first.
- `src/background/run.ts` — verify `SessionPrompt.abort` exists (it does; check signature).

**Verification:** unit test — start a `runOnce`, immediately call `Manager.remove` + `Engine.abort`, assert no `LoopRun` is written and the session is finalized.

### 1.4. Double-scheduling (TUI timer + server Scheduler)

**Problem:** `src/cli/cmd/tui/feature-plugins/loops/runner.ts:184-189` runs a local `setInterval` and `engine.ts:329-339` arms the server's `Scheduler.register`. Both call `runOnce`; the server's single-flight deduplicates but the work is wasted and the "next fire time" lives in two places.

**Fix:** make the TUI _not_ a scheduler. The TUI's local timer is a UI hint, not a trigger:

- Rename the TUI's `arm`/`disarm` to `subscribeTicker` / `unsubscribeTicker` and document them as "for snappy sidebar animation only; the server runs the real schedule."
- The TUI's local ticker is **idempotent**: it does not call `runOnce` itself, it only nudges the local Solid store to re-read the latest `Runtime` from the server via `LoopApi.getRuntime(id)`. (The TUI already subscribes to bus events for actual state changes; the ticker is purely cosmetic.)
- The server's `Scheduler.register` is the only writer of run records.

**Files to touch:**

- `src/cli/cmd/tui/feature-plugins/loops/runner.ts:180-211` — refactor `arm`/`disarm`/`syncAll`.
- Doc comment update in `runner.ts:1-9`.

**Verification:** in a TUI smoke test, start an interval loop, leave the TUI open for two ticks, assert only one `LoopRun` is created per tick (not two).

### 1.5. Bus event typing regression

**Problem:** `src/loop/engine.ts:54-63` defines `RunFinished.status` as `z.string()` instead of `LoopRunStatusSchema`. The SDK inherits the loose type, and consumers can't trust it. Same issue: `RunFinished.sessionID` is `z.string().optional()` but is always set at publish time.

**Fix:**

- `RunFinished.status: LoopRunStatusSchema` (import from `schema.ts:52`).
- `RunFinished.sessionID: z.string()` (not optional).
- Add a `RunFinished.additions`, `RunFinished.deletions`, `RunFinished.files` (from the `LoopRun` diff fields) so the TUI can update its stats without a follow-up `listRuns` call.

**Files to touch:** `src/loop/engine.ts:33-71`.

After the fix, regenerate the SDK with `bun script/build.ts` in `packages/sdk/js/` (per AGENTS.md).

### 1.6. `Runtime` rehydration from storage on `restore()`

**Problem:** `engine.ts:361-368` (`restore`) re-arms timers but never rehydrates `live: Map` from `Manager.listRuns`. After a restart the sidebar shows idle/0 for every loop even though the storage has a `lastError` and `lastRunAt`.

**Fix:** in `restore()`, for each def call `Manager.listRuns(id, 1)` and reconstruct a `Runtime` with `{ status: "idle", runs: countRuns, lastRunAt, lastError, lastSessionID }`.

**Files to touch:** `src/loop/engine.ts:361-368`.

### 1.7. `reconcileInterrupted` integration

**Problem:** If the server crashes mid-run, the `LoopRun` is left in `"running"` status and the `inFlight` map is empty. The next `restore()` doesn't reconcile.

**Fix:** in `restore()`, call `Manager.listAllRunsAcrossLoops()` and for any run with `status: "running"` and `startedAt < now() - LOOP_RUN_LEASE_MS` (15s, same as `BackgroundRun.LEASE_TIMEOUT_MS`), mark it as `"orphaned"` via a new `Manager.orphanRun(id, runID)` method.

**Files to touch:**

- `src/loop/manager.ts` — add `orphanRun`.
- `src/loop/engine.ts:361-368` — call it during restore.

### 1.8. Engine docstring correction

**Problem:** `engine.ts:1-14` overstates the engine's autonomy (claims "the Goal system iterates autonomously" — actually it's a single `prompt.command` call) and incorrectly claims live state is tracked (it's in-memory only, not rehydrated — fixed in §1.6).

**Fix:** rewrite the docstring to accurately describe: (1) drives each stage via `SessionPrompt.Service.command({ command: "goal" })`; (2) the agent's own goal loop is responsible for iteration; (3) the engine handles scheduling, single-flight, cap enforcement, and persistence.

**Files to touch:** `src/loop/engine.ts:1-14`.

## Phase 4 · Nice-to-haves (lower priority)

- **API response consistency:** `loop.delete` returns `c.json(true)`; `loop.toggle` returns the full entity. Pick one. Recommend: `boolean` for state-mutating endpoints, full entity for the upsert/toggle.
- **`LoopRuntime` DTO source:** `routes/loop.ts:45-54` hand-rolls `LoopRuntimeSchema` instead of deriving it from `engine.ts:77-83`. Import the engine's `Runtime` and extend with `loopID` so they can't drift.
- **`RunFinished.sessionID` carry:** engine already publishes it; the TUI needs it to open the source session — currently consumers have to listen to `RunStarted` first.
- **Performance:** add a 2s `listRuns` cache (like `BackgroundRun.listCache` at `run.ts:423-449`) to prevent 50 disk reads on every sidebar poll.
- **`generateFromDescription` sandbox:** the route creates a real session with full tool access. Consider a read-only agent for this call.
- **`parseDuration` upper bound:** add `MAX_INTERVAL_MS = 30 * 24 * 60 * 60 * 1000` (30 days) enforced in `validateDefinition`.
- **`agent` allow-list in `definitionFromGenerated`:** reject model-invented agent names against the known agent set.
- **JSDoc on public types:** `LoopDefinition`, `LoopStage`, `LoopRun`, `LoopTrigger`, `LoopRunStatus` in `schema.ts` and `Runtime` in `engine.ts` — add `@description` for SDK consumers.

4. **Manual smoke test** — in a TUI session:
   - Create an interval loop with `intervalMs: 30000`.
   - Leave the TUI open for 2 minutes and assert exactly 4 run records appear in the sidebar.
   - Quit the TUI, wait 1 minute, restart, assert the latest 4 runs are visible (rehydration).
   - Start a long-running loop, hit "Abort", assert the session is cancelled and the run is marked `"cancelled"`.
   - Delete a loop while it has an in-flight run, assert no orphan `LoopRun` is created.
5. **Open two TUI windows on different project directories** — create a loop in each with the same id, assert the sidebars show distinct state (Instance.state isolation).
