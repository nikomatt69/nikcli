# nikcli Package — Architecture Deep Dive

## Overview

The `packages/nikcli` package is the main application in the nikcli monorepo. It consists of ~274 source files across 68 directories, totaling ~1.9MB. The architecture follows a layered design with **Effect-TS** dependency injection, **Hono** HTTP server, and **Zod** validation throughout.

---

## 1. Entry Points & CLI

**File**: `src/index.ts`

The application starts here as a CLI tool using **yargs**:

- Global middleware initializes logging, environment variables (`NIKCLI=1`, `AGENT=1`)
- Registers 30+ commands: `run`, `serve`, `generate`, `debug`, `auth`, `agent`, `workspace-serve`, etc.
- Error handling catches `NamedError` and formats stack traces
- On process exit, explicitly calls `process.exit()` to prevent hanging subprocesses

**CLI commands** live under `src/cli/cmd/` with subdirectories for TUI, remote, etc.

## 2. Server Layer

**File**: `src/server/server.ts` (974 lines)

The server uses **Hono** as the HTTP framework and **Bun.serve** as the runtime.

### Server Startup (`Server.listen()`)

```
Bun.serve({ port, hostname, fetch: App().fetch, websocket })
  → CORS middleware
  → Workspace auto-sync (in dev mode)
  → mDNS publishing (optional)
```

### Middleware Pipeline (in order)

1. **Error handling** — NamedError → JSON responses with status codes
2. **Share routes** — `/s/:shareID`, `/share/:shareID` (public)
3. **User auth middleware** — `userAuthMiddleware()` from routes/users
4. **Server auth** — Password auth (basicAuth), Bearer tokens (mobile), Tailscale auth
5. **Request logging** — Timing for each request
6. **CORS** — Local dev origins, Tailscale, nikcli.store, custom whitelist
7. **Global routes** — `/global/health`, etc.
8. **Instance/Workspace context** — Reads `directory` or `workspace` from query/header, resolves workspace target:
   - Remote workspace → proxy request to remote server
   - Local workspace → switch directory
   - Wraps remaining middleware in `WorkspaceContext.provide()`
9. **OpenAPI docs** — `/doc`
10. **Experimental HTTP API bridge** — `HttpApiBridge` for routes migrated to Effect HTTP API
11. **Domain routes** — `/project`, `/session`, `/permission`, `/question`, `/provider`, etc.
12. **Top-level endpoints** — `/agent`, `/skill`, `/command`, `/lsp`, `/formatter`, `/auth`, `/path`, `/vcs`, `/log`, `/event` (SSE), `/instance/dispose`
13. **Catch-all** — proxies to `https://app.nikcli.store` for web UI

### Route Files (`src/server/routes/`)

Each file returns a Hono sub-app:
| Route | File | Key Endpoints |
|-------|------|--------------|
| `/session` | `session.ts` | CRUD, init, fork, abort, revert, prompt (LLM interaction), messages, todos, background jobs |
| `/project` | `project.ts` | List, create, update, current project |
| `/permission` | `permission.ts` | List, reply to permission asks |
| `/question` | `question.ts` | Ask, reply, reject questions |
| `/provider` | `provider.ts` | List providers, auth endpoints, API proxy |
| `/config` | `config.ts` | GET/PATCH configuration |
| `/file` | `file.ts` | File read/write/search |
| `/tui` | `tui.ts` | Terminal UI communication |
| `/mcp` | `mcp.ts` | MCP server management (connect, disconnect, toggle) |
| `/connectors` | `connectors.ts` | Connector registry |
| `/chatbot` | `chatbot.ts` | Chatbot integration |
| `/companion` | `companion.ts` | Companion services |
| `/mobile` | `mobile.ts` | Mobile app endpoints (Expo) |
| `/users` | `users.ts` | User authentication (register, login, status) |
| `/global` | `global.ts` | Health check, global state |
| `/analytics` | `analytics.ts` | Usage analytics |
| `/experimental` | `experimental.ts` | Workspace CRUD, resource inspection, tool listing |
| `/pty` | `pty.ts` | PTY (pseudo-terminal) management |

### Experimental HTTP API (`src/server/httpapi/`)

New Effect-TS based API using `effect/unstable/httpapi`:

- **`workspace.ts`** — Workspace endpoints (adaptors, create, list, remove, restore, sessionRestore)
- **`bridge.ts`** — Bridges old Hono routes to new Effect API, selectively migrating routes by pattern matching
- **`public.ts`** — Public HTTP API definition

## 3. Dependency Injection (Effect-TS)

**Files**: `src/effect/`

The entire system uses **Effect-TS** for dependency injection:

| File                | Purpose                                                                         |
| ------------------- | ------------------------------------------------------------------------------- |
| `runtime.ts`        | Core runtime: `runPromiseWithLayer()`, `makeRuntime()`, `withCurrentInstance()` |
| `instance-state.ts` | Per-instance scoped state via `ScopedCache`                                     |
| `instance-ref.ts`   | Instance context (directory, worktree, project)                                 |
| `instance-scope.ts` | Scope management for isolated instances                                         |
| `with-instance.ts`  | `withInstanceAsync()` for running code in an instance context                   |

**Pattern used everywhere**:

```typescript
function runSession<A, E>(effect: Effect.Effect<A, E, Session.Service>) {
  return runPromiseWithLayer(Session.defaultLayer, withCurrentInstance(effect))
}
```

Each service module exports:

- An `Interface` type
- A `Service` class extending `Context.Service`
- A `layer` (Effect Layer) with implementation
- A `defaultLayer` export

## 4. Session System

**Files**: `src/session/` (26 files)

### Data Model

- **Session**: `id`, `title`, `directory`, `parentID` (forking), `workspaceID`, `model`, `agent`
- **Messages**: V2 system with `MessageV2.Info` (`id`, `role`, `parts`, `time`)
- **Parts**: `TextPart`, `ReasoningPart`, `ToolPart`, `FilePart`, `StepStartPart`, etc.
- **Storage keys**: `["session", projectID, sessionID]`, `["message", sessionID, messageID]`, `["part", messageID, partID]`

### Key Files

| File                 | Purpose                                                                                                    |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| `index.ts`           | Session CRUD, create, list, get, fork, revert, delete, update                                              |
| `message-v2.ts`      | Message/part types, storage operations, content length management                                          |
| `prompt.ts` (79KB!)  | **Core LLM prompting loop** — builds system prompt, manages tool calls, MCP integration, structured output |
| `processor.ts`       | **Session processing pipeline** — doom-loop detection, delta coalescing, retry logic                       |
| `llm.ts`             | **LLM client** — wraps AI SDK + `@nikcli-ai/llm`, provider selection, header building, tool conversion     |
| `compaction.ts`      | Context compaction when token limits approached                                                            |
| `summary.ts`         | Session summarization                                                                                      |
| `system.ts`          | System prompt assembly (tools, context, permissions)                                                       |
| `status.ts`          | Session status tracking (active, idle, completed, error)                                                   |
| `todo.ts`            | Todo list management per session                                                                           |
| `revert.ts`          | Session state reversion                                                                                    |
| `retry.ts`           | Retry logic for failed tool calls                                                                          |
| `delta-coalescer.ts` | Batches disk writes for streaming deltas (~500 writes → ~10-20)                                            |
| `stats.ts`           | Usage statistics                                                                                           |
| `native-executor.ts` | Native tool execution                                                                                      |

### LLM Interaction Flow

```
SessionPrompt (prompt.ts)
  → builds system prompt (SystemPrompt)
  → resolves tools (ToolRegistry.tools)
  → calls LLM (LLM.stream)
  → on tool calls → SessionProcessor.create
    → doom-loop check
    → execute tool
    → return result to LLM
  → on completion → store message/parts
  → stream deltas via Bus events
```

## 5. Tool System

**Files**: `src/tool/` (60+ files)

### Core (`tool.ts`)

```typescript
Tool.define(id, init | AuthoredDef) → Tool.Info
  - parameters: Zod schema
  - execute: Effect.Effect<Result>
  - executeAsync: Promise<Result> (compat)
```

### Tool Context

Each tool receives:

- `sessionID`, `messageID`, `agent`, `abort`
- `metadata()` — for sending metadata back
- `ask()` — for requesting permissions

### Registry (`registry.ts`)

- Loads built-in tools (bash, read, glob, grep, edit, write, task, etc.)
- Loads custom tools from `{tool,tools}/*.{js,ts}` in config directories
- Loads plugin tools
- Filters by model capabilities (e.g., `apply_patch` only for GPT models, `codesearch`/`websearch` require specific providers)
- Slim mode for fast agents
- Permission-based filtering

## 6. Agent System

**File**: `src/agent/agent.ts` (29.5KB)

### Agent Types

- **Primary agents** (`mode: "primary"`): `ralph`, `build`, `plan` — autonomous loop agents
- **Subagents** (`mode: "subagent"`): Dedicated task agents
- **General agents** (`mode: "all"`): `general`, `explore`, `fast-explore`, `planner`, etc.

### Agent Configuration

- **Permissions**: `PermissionNext.Rule` array defining tool access rules
- **Tool restrictions**: `SUBAGENT_TOOLSETS` maps agent names to allowed tools
- **System prompts**: Loaded from `prompt/*.txt` files
- **Model**: Can override default model per agent

### Default Agents (built-in)

```
ralph   → autonomous loop, full access
build   → implementation, plan_enter allowed
plan    → planning, restricted file writes
general → general purpose, todoread/todowrite denied
explore → codebase inspection (read-only + bash)
fast-explore → quick inspection (read-only, no bash)
planner → planning (search tools)
researcher → research (web + code search + memory)
code-reviewer → code review
debugger → debugging
refactor → refactoring
```

## 7. CLI Entry Points & TUI Architecture

### Binary Bootstrap

- **`bin/nikcli`**: Shell script that finds platform-specific pre-compiled binary (`nikcli-darwin-arm64`, etc.) in `node_modules/` and spawns it
- **`src/index.ts`**: TypeScript entry compiled via `Bun.build()` into standalone binaries for 12+ platform targets

### TUI Architecture

The TUI is built with **SolidJS** + **OpenTUI** (`@opentui/solid`, `@opentui/core`):

| File                              | Role                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| `src/cli/cmd/tui/thread.ts`       | TUI entry command. Spawns Web Worker (`worker.ts`), sets up RPC, handles CLI options |
| `src/cli/cmd/tui/worker.ts`       | Background worker running HTTP server + event streaming + RPC proxy                  |
| `src/cli/cmd/tui/app.tsx`         | Main SolidJS app with context providers (SDK, Route, Theme, Keybind, Server, etc.)   |
| `src/cli/cmd/tui/context/sdk.tsx` | SDK context creating `NikcliClient`, SSE event subscription, SolidJS event bus       |

**Communication modes**:

1. **Direct RPC** (Worker): Main thread ↔ Worker via `Rpc.client<T>` for bidirectional HTTP
2. **HTTP/SSE**: Client connects to server, events stream via `/event` endpoint
3. **WebSocket**: Used by mobile/remote connections

## 8. SDK Package (`packages/sdk/js/`)

**Package**: `@nikcli-ai/sdk`

### Exports

- `./client` → `createNikcliClient()` (auto-generated typed client)
- `./server` → `createNikcliServer()` (spawns `nikcli serve`), `createNikcliTui()`
- `./v2` → Current v2 SDK with identical patterns from v2 OpenAPI spec
- `./crypto`, `./cloud` → Utility sub-exports

### Auto-Generation Workflow

1. `bun dev generate` dumps OpenAPI spec from Hono server to `openapi.json`
2. `@hey-api/openapi-ts` generates typed client code (`sdk.gen.ts`, `types.gen.ts`, `client.gen.ts`)
3. `NikcliClient` class exposes typed methods for all server endpoints

## 10. Remote & Companion Packages

### Remote (`packages/remote/`)

**Purpose**: WebSocket terminal streaming to remote devices (mobile, browser) via QR code

- `RemoteServer` class: HTTP + WebSocket server, PTY proxy, heartbeat, session timeout
- `TunnelManager`: Public tunnel creation (localtunnel)
- QR code generation for mobile connection
- Ghostty terminal emulator (WASM) for browser rendering

### Companion (`packages/companion/`)

**Purpose**: WebSocket bridge for browser UI ↔ nikcli CLI instances

- Routes: `/ws/cli/:sessionId` (CLI connects), `/ws/browser/:sessionId` (browser connects)
- Bridges STDIO from nikcli CLI to browser WebSockets
- Manages session state, permission routing, CLI process lifecycle
- Zustand store for web UI state

## 13. Storage System

**File**: `src/storage/storage.ts` (329 lines)

File-based JSON storage with:

- **In-memory cache**: Read-through with 5-second TTL
- **File locking**: Read/write locks prevent concurrent modification
- **Hierarchical keys**: `["session", projectID, sessionID]`
- **Migrations**: Schema migration support
- **Data directory**: `Global.Path.data/storage/`

## 14. Workspace System

**Files**: `src/workspace/`

Manages remote workspaces (worktree or container-based):

- **Adaptors**: Worktree adaptor (local git worktrees), Container adaptor (Docker/Podman)
- **SSE sync**: Event loop connects to remote workspace via SSE, mirrors events locally
- **Event mirroring**: Session status, permission asks/replies — mirrored across workspaces
- **Restore**: Reconnects and replays buffered events

### Workspace HTTP API (`src/server/httpapi/workspace.ts`)

```
GET  /experimental/workspace/adaptor          → list adaptors
POST /experimental/workspace/:id              → create workspace
GET  /experimental/workspace/                 → list workspaces
DELETE /experimental/workspace/:id            → remove workspace
POST /experimental/workspace/:id/restore      → restore connection
POST /experimental/workspace/:id/session/:sid/restore → session restore
```

## 16. Data Flow Summary

```
CLI (yargs) → command handler
    ↓
Server.start() → Bun.serve(Hono app)
    ↓
Client request (HTTP/SSE/WS)
    ↓
Middleware: auth → instance context → workspace resolution
    ↓
Route handler → Effect-TS service (runPromiseWithLayer)
    ↓
Business logic (Session, Agent, Provider, Storage)
    ↓
Response (JSON) / SSE stream (Bus events)
```

### Session LLM Loop (Core Flow)

```
1. Client POST /session → Session.create()
2. Client POST /session/:id/prompt → SessionPrompt.start()
3. System prompt built from: Agent config + Tools + Context files + Permissions
4. Tools resolved via ToolRegistry.tools(model, agent)
5. LLM call via Provider.App.stream() (using ai-sdk + @nikcli-ai/llm)
6. On tool_calls:
   a. SessionProcessor.create() — executes tool, detects doom-loops
   b. Tool.execute() or Tool.executeAsync()
   c. Result streamed back to LLM
7. On completion: messages/parts persisted to Storage, Bus events published
8. Client receives streaming updates via SSE endpoint /event
```

## 17. Key Design Patterns

1. **Effect-TS everywhere**: Services, Layers, `Effect.gen(function* (){})` for async
2. **`runPromiseWithLayer`**: Bridges Effect to Promise at the boundaries (route handlers)
3. **`withCurrentInstance`**: Provides current directory/worktree/project context to effects
4. **Zod validation**: All inputs validated with Zod schemas
5. **Result patterns**: Tools return `{ title, metadata, output }` instead of throwing
6. **Bus events**: Decoupled communication via `Bus.publish`/`Bus.subscribeAll`
7. **SSE streaming**: `/event` endpoint for real-time client updates (30s heartbeat)
8. **File-based storage**: JSON files with locking + in-memory cache
9. **Plugin extensibility**: Tools and providers can be added via plugins
10. **Workspace federation**: Multi-location collaboration via SSE sync + event mirroring
