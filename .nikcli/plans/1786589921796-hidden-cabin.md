# nikcli TUI — Architecture Analysis

This is an **analysis-only plan** that documents the structure and key abstractions of nikcli's terminal user interface. No code changes are proposed; this is a reference for future work.

---

## 1. Location

The TUI is **not** a standalone package. It is a yargs subcommand of `nikcli`, located at:

```
packages/nikcli/src/cli/cmd/tui/
```

Running `nikcli` with no arguments launches the TUI (the default `$0` command). Other CLI subcommands (account, auth, mcp, etc.) use `@clack/prompts` for one-shot interactive flows — they do not enter the TUI runtime.

---

## 2. Stack

| Layer          | Technology                    | Version / Notes                                                                              |
| -------------- | ----------------------------- | -------------------------------------------------------------------------------------------- |
| Renderer       | `@opentui/core`               | `0.4.5` (patched in-repo) — terminal primitives, renderables, kitty keyboard, mouse, palette |
| Solid bindings | `@opentui/solid`              | `0.4.5` — `render`, `useRenderer`, `useKeyboard`, `useTerminalDimensions`, `useTimeline`     |
| Reactivity     | `solid-js` + `solid-js/store` | `createSignal`, `createStore`, `createMemo`, `createEffect`, `produce`, `reconcile`, `batch` |
| Process split  | `Bun.spawn` + RPC             | TUI process spawns a worker that runs `Server.listen` and forwards `GlobalBus` events        |
| CLI parser     | `yargs`                       | `cli-main.ts` dispatches subcommands                                                         |

There is **no** Hono, no Express, no Redux/Zustand. The renderer talks to the server via the generated `@nikcli-ai/sdk/httpapi` client through an RPC channel.

---

## 3. Entry points

| Step | File                                        | What it does                                                                                                                              |
| ---- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `packages/nikcli/src/cli-main.ts`           | Builds yargs parser, registers `$0` → `TuiThreadCommand`                                                                                  |
| 2    | `packages/nikcli/src/cli/cmd/tui/thread.ts` | `TuiThreadCommand` handler — spawns `worker.ts`, sets up RPC, calls `tui(input)`                                                          |
| 3    | `packages/nikcli/src/cli/cmd/tui/worker.ts` | Child Bun process — runs `Server.listen`, exposes RPC methods (`fetch`, `server`, `mobileToken`, `subscribe`, `shutdown`, …)              |
| 4    | `packages/nikcli/src/cli/cmd/tui/app.tsx`   | `tui()` — creates the CLI renderer, wraps the tree in ~22 providers, mounts `<App />` via `render(() => <Tree/>, renderer)`               |
| 5    | `app.tsx` `<App />`                         | `<Switch>` router keyed on `route.data.type` mounts `<Home>` / `<Session>` / `<Workspace>` / `<PluginRouteBoundary>` / `<LegacyRedirect>` |

### Renderer config (`app.tsx:101-121`)

```ts
{
  targetFps: 45,
  useThread: shouldUseRendererThread(),  // false on Windows (sync writer)
  useKittyKeyboard: {},
  useMouse: tuiCfg.mouse ?? true,
  consoleOptions: { keyBindings: [{ name: "y", ctrl: true, action: "copy-selection" }] },
}
```

There is also a **drive mode** (`NIKCLI_DRIVE=1`) that wraps the renderer in `@nikcli-ai/simulation/frontend.Drive.create(...)` for deterministic PTY-free testing.

## 6. State management

**Three layers, no external store.**

| Layer                | Where                               | Lifetime                                                      | Examples                                                                                                                                                                                                                                    |
| -------------------- | ----------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Server-cached**    | `SyncProvider` (`context/sync.tsx`) | Reconciles against HTTP `/sync` payload                       | `sessions`, `providers`, `agents`, `commands`, `permission`, `question`, `mcp`, `lsp`, `session_diff`, `todo`, `vcs`, `workspace`, `config`, `formatter`, `provider_auth`, `provider_next`, `provider_default`, `session_status`, `message` |
| **Local persistent** | `KVProvider` (`context/kv.tsx`)     | JSON file at `~/.local/state/nikcli/kv.json`, debounced 250ms | `onboarding_complete`, `skipped_version`, `terminal_title_enabled`, theme choice, plugin KV state                                                                                                                                           |
| **Local ephemeral**  | Per-context `createStore`           | Component lifetime                                            | route, theme mode, local agent/model/mode, prompt text, tabs, dialog stack, toasts                                                                                                                                                          |

### Event flow

- **Server → TUI**: `worker.ts` forwards `GlobalBus` events as `Rpc.emit("global.event", envelope)`. `SDKProvider` subscribes via `EventSource.subscribe` and re-emits on a global emitter. `SyncProvider` reconciles by event `type`.
- **TUI → Server**: HTTP through the generated `@nikcli-ai/sdk/httpapi` client (`createNikcliClient` in `context/sdk.tsx`).

### Key reactive patterns

- `createStore` + `produce` + `reconcile` for fine-grained mutations of large nested objects.
- `createSignal` for small primitives.
- `createMemo` for derived computations.
- `createEffect(on(...))` for side effects, often `defer: true`.
- `batch()` for grouped updates.
- Custom helpers in `util/signal.ts`: `createDebouncedSignal`, `createLatestOnlyAsync`.

## 7. Routing

`context/route.tsx` declares a `Route` union:

```ts
type Route =
  | HomeRoute       { type: "home";       initialPrompt?; workspaceID? }
  | SessionRoute    { type: "session";    sessionID;       initialPrompt?; workspaceID? }
  | PluginRoute     { type: "plugin";     id;              data?; workspaceID? }
  | ChangesRoute    { type: "changes";    sessionID;       workspaceID? }
  | SessionTreeRoute{ type: "tree";       sessionID?;      workspaceID? }
  | GitGraphRoute   { type: "git-graph";  sessionID?;      workspaceID? }
  | GitHubRoute     { type: "github";     sessionID?;      workspaceID? }
  | WorkspaceRoute  { type: "workspace";  tab?: "tree"|"changes"|"graph"|"github"; sessionID?; workspaceID? }
```

`<App />` uses `<Switch><Match>` keyed on `route.data.type`. Mutations go through `route.navigate({...})`. The legacy single-tab types (`changes`, `tree`, `git-graph`, `github`) redirect to `Workspace` with the matching tab. `NIKCLI_ROUTE` env var (JSON-encoded) overrides the initial route.

## 8. Theming

`context/theme.tsx` (~667 lines) is the most important context.

- **97 bundled themes** under `context/theme/*.json` (catppuccin, dracula, tokyonight, nord, gruvbox, github, plus nikcli originals like `nikcli.json`, `brain.json`, `nikoemme-dark.json`).
- **User themes** auto-loaded from `~/.config/nikcli/themes/*.json` or any ancestor `.nikcli/themes/*.json` via `Bun.Glob`.
- **`Theme` type** has 56 semantic colors organized into: 7 brand (`primary/secondary/accent/error/warning/success/info`), 5 text/background levels, 3 border levels, 11 `diff*` colors, 13 `markdown*` colors, 9 `syntax*` colors.
- **Resolution**: `resolveTheme(themeJson, mode)` handles hex strings, ANSI codes, refs to `defs`, and `transparent/none`. Modes `dark | light | system` follow the terminal palette.
- **Reactivity**: `ThemeProvider` exposes a **Proxy** so `theme.primary` is a reactive read.
- Helpers: `selectedForeground(theme, bg?)` (luminance-based contrast), `tint(base, overlay, alpha)`, `addTheme(name, data)` (plugin API).
- Components consume colors directly: `<box borderColor={theme.border}><text fg={theme.text}>` — no CSS, no styled-components.

The `dialog-theme-create.tsx` dialog writes new themes into the user's themes folder.

## 9. Dialog system

A simple stack-based manager in `ui/dialog.tsx`:

```ts
const dialog = useDialog()
dialog.replace(() => <DialogFoo />)
dialog.push(() => <DialogBar />)
dialog.clear()
dialog.stack  // current stack
```

- `<Dialog />` is a centered modal-overlay that fades in via OpenTUI's `useTimeline()`.
- Sizing modes: `medium | large | xlarge | full` (capped at 120 columns for content legibility).
- Escape closes top; Ctrl+C clears entire stack unless top is interactive.
- Mouse-up-outside closes; copy-on-selection via `Clipboard` + `useToast`.

### Primitives (`ui/`)

| File                           | Role                                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------- |
| `dialog.tsx`                   | Stack + `<Dialog />` shell                                                               |
| `dialog-select.tsx`            | **`DialogSelect<T>`** — fuzzy-searchable categorised list, the workhorse for ~30 dialogs |
| `dialog-prompt.tsx`            | Modal text input with `busy` spinner                                                     |
| `dialog-confirm.tsx`           | Y/N confirm (safe default = cancel)                                                      |
| `dialog-alert.tsx`             | OK-only modal                                                                            |
| `dialog-help.tsx`              | `?` key help overlay                                                                     |
| `dialog-export-options.tsx`    | Export config                                                                            |
| `toast.tsx`                    | ToastProvider (cap 3, info/success/warning/error with default 3s/3s/5s/7s)               |

### `DialogSelect<T>` internals

- `createStore({ selected, filter, input: 'keyboard' | 'mouse' })`.
- Memo chain: `filtered` (fuzzysort) → `grouped` (by category) → `flat` → `selected`.
- Mouse-aware: tracks `store.input` so synthetic mousemove events during filter changes don't desync the keyboard cursor.
- Custom keybinds via `DialogSelectKeybind<T>` (`allowEmpty` for "scope change" actions).
- Imperative `ref?: (ref: DialogSelectRef<T>) => void` for parent sync (filter value, filtered list).

## 10. Command palette (`component/dialog-command.tsx`)

`CommandProvider` is the global command registry. Every command is a `CommandOption`:

```ts
{
  title: string
  value: string                    // e.g. "model.list"
  category?: string                // for grouping in the palette
  keybind?: string                 // keybind name from keybinds config
  slash?: { name: string; aliases?: string[] }
  suggested?: boolean
  hidden?: boolean
  enabled?: boolean
  onSelect: (dialog) => void       // typically dialog.replace(...) or route.navigate(...)
}
```

Commands are registered globally with `command.register(() => [...])` — `app.tsx:589-1262` contains the bulk of the built-in commands. The palette opens via the `command_list` keybind (default `<leader> x` or `<leader>+` x) and is itself a `DialogSelect`. Plugins add commands through `registerGlobalCommand(...)`.

Slash commands flow through `component/prompt/autocomplete.tsx`: typing `/` shows the filtered list, selecting runs `onSelect`. The `TuiEvent.CommandExecute` schema (`event.ts`) lets server-side code trigger commands through the same pipeline.

## 11. Plugin runtime (`plugin/`)

The TUI has a **two-version** plugin API:

- **V1**: legacy `TuiPlugin` function from `@nikcli-ai/plugin/tui`.
- **V2**: declarative `Plugin.define({ id, setup(ctx) { ... } })` from `@nikcli-ai/plugin/v2/tui`.

Plugin surface (`plugin/api.tsx`):

```ts
ctx.ui.slot("sidebar.content", (props) => <View sessionID={String(props.sessionID)} />)
ctx.registerCommand({ ... })
ctx.kv.set("...", value)
ctx.navigate({ ... })
```

Slots are declared in `plugin/slots.tsx` and consumed via `<TuiPluginRuntime.Slot name="app.bottom" />` / `app` / `sidebar.content` / etc. Slot errors are caught and shown as a single toast.

`plugin/reload.ts` watches source files (mtime-based) and re-imports plugins on edit, busting the LRU cache and re-registering routes — true hot reload.

## 12. Keybindings

- `util/keybind.ts` exports `Keybind.parse / match / fromParsedKey / toString` (built on `ParsedKey` from `@opentui/core`).
- `context/keybind.tsx` registers a global `useKeyboard(async evt => ...)` listener; when a leader-key sequence completes, it resolves the keybind through the parsed config.
- `KeybindProvider` reads `sync.data.config.keybinds` (so the server config is the source of truth).
- `component/textarea-keybindings.ts` maps `input_*` config keys into OpenTUI `KeyBinding[]` for the composer textarea.

Default leader key is configurable; `<leader> x` opens the command palette.

## 13. The prompt composer

`component/prompt/index.tsx` (~82 KB / ~2k lines) is the single largest TUI component. It owns:

- `<textarea ref>` with `useTextareaKeybindings`.
- Bottom toolbar (model, agent, mode, voice, MCP, image, mobile buttons).
- Autocomplete (`./autocomplete.tsx`, anchored via BoxRenderable position polling).
- History (`./history.tsx`, `PromptHistoryProvider` backed by JSONL).
- Stash (`./stash.tsx`) — stash draft on interrupt.
- Frecency weighting (`./frecency.tsx`).
- Voice input via a Swift `AVAudioRecorder` shim.
- Paste-from-clipboard (incl. image → blob via `util/prompt-blob.ts`).
- Drag-drop, jobs inline strip, ghost-text prompt frames.
- Submit / interrupt / model-pick hot paths.
- Server-side submission via `useSDK`.

Exposed through `PromptRefProvider` (`context/prompt.tsx`) so non-`<Prompt>` consumers get an imperative `{ focused, current, set, reset, blur, focus, submit }` handle — used by voice input, dialogs, plugin code.

## 14. Process & RPC topology

```
┌────────────────────────┐         RPC (worker_threads)          ┌────────────────────────┐
│ TUI process            │  <──────────────────────────────────>  │ Worker process          │
│ (OpenTUI renderer +    │   • fetch()         (HTTP via worker) │ (Server.listen +         │
│  Solid component tree) │   • server.*        (startServer,     │  GlobalBus → RPC bridge) │
│                        │      mobileToken)                    │                          │
│                        │   • subscribe/unsubscribe (SSE)       │  /sync, /event,          │
│                        │   • shutdown                          │  /session/*, /provider/* │
│                        │   • reload                            │  …                       │
└────────────────────────┘                                       └────────────────────────┘
```

When `--port` / `--hostname` are passed, the TUI falls back to real HTTP/SSE instead of in-process RPC.

## 15. Cross-cutting concerns

| Concern             | Mechanism                                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| HTTP server / RPC   | Worker runs `Server.listen()`; TUI uses `createNikcliClient({ baseUrl, fetch: createWorkerFetch(client) })`                    |
| Sessions / messages | `SyncProvider` reconciles `/sync` payload — `sync.session.get(id)`, `sync.data.message[sessionID]`                             |
| Tools               | TUI imports tool types from `@/tool/*` for typing only; execution is server-side                                               |
| Providers / models  | Cached in `sync.data.provider`, `provider_next`, `provider_auth`. `local.model.set({...})` mutates local state; sent on submit |
| Permissions         | `sync.data.permission[sessionID]` queue; `routes/session/permission.tsx` renders the prompt UI                                 |
| MCP                 | `sync.data.mcp` — count and status in home/sidebar                                                                             |

## 18. Summary

- The nikcli TUI is **OpenTUI + Solid.js**, located in `packages/nikcli/src/cli/cmd/tui/`.
- It's **not** a separate package or library — it is the long-lived interactive shell that bootstraps from the `nikcli` binary's default subcommand.
- All short-lived CLI utilities use `@clack/prompts`; the TUI never does.
- State is **100% Solid stores + contexts** — no Redux/Zustand/etc.
- Theming is **JSON-driven** with a reactive `Proxy` over 56 semantic colors.
- Modals are **stack-based** (`DialogProvider`).
- The command palette (`dialog-command.tsx`) is the single source of truth for both slash commands and keybinds.
- Plugins (V1 + V2) slot into named render positions without forking core components.
- The server runs in a child Bun process; the TUI communicates through RPC and generated HTTP/SSE.

No code changes proposed.
