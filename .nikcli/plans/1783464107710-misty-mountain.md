# Plan: Adopt Effect-Smol / Opencode Migration Patterns

## Goal Interpretation

Valutare cosa conviene prendere da `.opencode/references/effect-smol/migration` e `.opencode/references/effect-smol/packages` per guidare una migrazione/rafforzamento Effect v4 in `packages/nikcli`, senza implementare modifiche in questa fase.

## Evidence Collected

- `packages/nikcli/package.json` already uses `effect@4.0.0-beta.65` and `@effect/platform-bun@4.0.0-beta.65`.
- `packages/nikcli/src/effect/runtime.ts` already implements a shared `Layer.makeMemoMap` and `ManagedRuntime.make(..., { memoMap })`, matching the migration guidance in `migration/layer-memoization.md`.
- `packages/nikcli/src/effect/instance-scope.ts` already uses v4 `Effect.callback` and `Fiber` to bridge legacy `Instance.provide` into structured Effect execution.
- `packages/nikcli/src/tool/tool.ts` already normalizes tool execution to `Effect.Effect`, while keeping `executeAsync` as a compatibility boundary.
- `packages/nikcli/src/worktree/index.ts` already adopts `Schema.Struct`, `Schema.TaggedErrorClass`, `Context.Service`, and explicit layers.
- `packages/nikcli/src/server/httpapi/bridge.ts` already uses `effect/unstable/http`, `@effect/platform-bun`, `Context`, and shared memoization for the HttpApi bridge.
- `packages/nikcli/src/util/effect-zod.ts` is already a local Effect Schema to Zod bridge and should remain a transition tool while schemas move to Effect Schema.
- `packages/nikcli/package.json` already has the relevant Effect packages; the first adoption steps should not add dependencies.

## What To Take From Migration Docs

### 1. Make Service Style Consistent

Adopt `Context.Service` as the only new-service pattern, following `migration/services.md`.

- Prefer `class Service extends Context.Service<Service, Shape>()("Service") {}` for richer modules.
- Prefer `const Service = Context.Service<Shape>("Service")` for small internal services.
- Use `yield* Service` inside `Effect.gen(function* () { ... })` as the default access pattern.
- Avoid reintroducing `Context.Tag`, `Effect.Tag`, static accessor proxies, or `.Default`/`.Live` layer naming.
- Name primary layers `layer` or `defaultLayer` only when matching existing nikcli module convention; use explicit suffixes such as `layerTest`, `layerMemory`, `layerBun`.

Target areas:

- `packages/nikcli/src/storage/storage.ts`
- `packages/nikcli/src/session/*.ts`
- `packages/nikcli/src/permission/*.ts`
- `packages/nikcli/src/project/*.ts`
- `packages/nikcli/src/tool/*`

### 2. Keep Boundary Compatibility, Move Internals To Effect

Use the pattern already present in `src/tool/tool.ts`: plain async/Hono/TUI boundaries call Effect services, but business logic lives in Effect-native services.

- Keep `executeAsync`, Hono route handlers, and legacy async entrypoints as thin adapters.
- New or migrated service methods should return `Effect.Effect<Success, DomainError, Requirements>`.
- Use `Effect.gen(function* () { ... })` for multi-step workflows.
- Use `Effect.fn("Name")` or `Effect.fnUntraced(...)` for reusable workflows once the surrounding module is Effect-native.

Target areas:

- `packages/nikcli/src/server/server.ts` route bodies still doing direct async work.
- `packages/nikcli/src/cli/cmd/**` command handlers.
- `packages/nikcli/src/tool/*.ts` tools still authored as promises.

### 3. Standardize Error Modeling

Take the `Schema.TaggedErrorClass` pattern from `migration/schema.md` and existing `src/worktree/index.ts`.

- Model expected domain failures as typed tagged errors.
- Catch expected failures with `Effect.catchTag` / `Effect.catchTags` at route/tool boundaries.
- Keep defects and unknown exceptions out of typed domain channels.
- For Cause handling, follow `migration/cause.md`: inspect `cause.reasons` and `Cause.has*` helpers instead of assuming recursive Cause shapes.

Target areas:

- `packages/nikcli/src/server/server.ts` global `onError` fallback can shrink as per-route typed errors improve.
- `packages/nikcli/src/provider/error.ts`
- `packages/nikcli/src/session/event-error.ts`
- `packages/nikcli/src/cli/error.ts`
- `packages/nikcli/src/storage/storage.ts`

### 4. Continue Schema-First Migration

Use Effect `Schema` for new domain/API/tool data shapes, and keep `zodObject(...)` only as a compatibility adapter.

Take these concrete v4 schema rules from `migration/schema.md`:

- `Schema.Union([A, B])`, not variadic union.
- `Schema.Tuple([A, B])`, not variadic tuple.
- `Schema.Literals(["a", "b"])` for multi-literals.
- `Schema.Record(key, value)`, not `Schema.Record({ key, value })`.
- `Schema.optionalKey(...)` when the key itself is optional.
- `Schema.optional(...)` only when `undefined` is a meaningful value.
- `Schema.withDecodingDefault*` and `Schema.OptionFromOptional*` helpers when defaults or `Option` are part of the domain model.
- `Struct` helpers for `pick`, `omit`, `partial`, `required`, and field mapping.
- `Schema.check(Schema.is*)` / `Schema.makeFilter(...)` for refinements.

Target areas:

- New route/tool input schemas.
- Existing zod-heavy modules once touched for feature work.
- `packages/nikcli/src/util/effect-zod.ts` should be updated only when new Effect Schema constructs are actually used.

### 5. Preserve Shared Layer Memoization

The current `src/effect/runtime.ts` is already aligned with `migration/layer-memoization.md`; keep building on it.

- Compose layers before one `Effect.provide` where possible.
- Reuse `sharedMemoMap` for HTTP API/platform services.
- Use `Layer.fresh` or `Effect.provide(..., { local: true })` only for tests or intentionally isolated resources.

Target areas:

- `packages/nikcli/src/effect/runtime.ts`
- `packages/nikcli/src/server/httpapi/bridge.ts`
- Effect service tests under `packages/nikcli/test/**/effect-service.test.ts`

### 6. Prefer Effect Platform Packages For New IO

From `packages/platform-bun`, `packages/platform-node`, and package docs, adopt platform services for new Effect-native IO.

- Use `@effect/platform-bun` layers for Bun runtime services where the code is already Effect-native.
- Prefer `FileSystem`, `Path`, `HttpClient`, `Terminal` style services over ad hoc globals for new Effect modules.
- Do not rewrite stable legacy IO all at once; use this for new/migrated modules.

Target areas:

- New filesystem-heavy service work.
- HttpApi routes that need file/path access.
- Tool implementations that are already moving to Effect-native bodies.

### 7. Use HttpApi As The Future Server Contract

Take the schema-first route definition style from `packages/effect/HTTPAPI.md` and continue migrating behind the existing bridge.

- Keep Hono as compatibility shell while moving endpoints into `src/server/httpapi/*`.
- Define endpoint params/query/payload/success/error with Effect Schema.
- Put status codes and encodings on schemas with `HttpApiSchema.status(...)` and `HttpApiSchema.as*` helpers when an endpoint needs non-default response behavior.
- Keep raw streaming endpoints (`/event`, prompt streaming) outside schema-encoded HttpApi until a streaming-compatible pattern is established.
- When modifying `src/server/server.ts` endpoints, update or extend `src/server/httpapi/*` and regenerate SDK if server endpoint contracts change.

Target areas:

- `packages/nikcli/src/server/httpapi/public.ts`
- `packages/nikcli/src/server/httpapi/bridge.ts`
- `packages/nikcli/src/server/routes/*.ts`
- `packages/nikcli/src/server/server.ts`

### 8. Use MCP Toolkit Ideas Selectively

From `packages/effect/MCP.md`, the main reusable idea is declarative toolkits with schema-defined parameters and separately provided implementations.

- Do not replace nikcli tools immediately.
- For new MCP-facing or agent-facing capabilities, consider grouping related tool definitions and implementations similarly to `Toolkit.make(...).toLayer(...)`.
- Keep stdout/stderr protocol discipline for stdio-like integrations.

Target areas:

- `packages/nikcli/src/mcp/*`
- `packages/nikcli/src/tool/registry.ts`
- Future MCP bridge/toolkit modules.

### 9. Adopt Migration Guardrails As Checks

Use migration docs as a static review checklist for future Effect changes.

- No `Effect.catchAll`; use `Effect.catch`.
- No `Effect.either`; use `Effect.result`.
- Avoid old `Either`/`decodeEither` style at migrated Effect Schema boundaries; use the v4 `Result`/`Exit` APIs called out in the migration docs.
- No `Effect.fork`; use `Effect.forkChild` or `Effect.forkDetach` intentionally.
- No `Runtime<R>` assumptions; use `Context<R>` and current runtime helpers.
- No `Scope.extend`; use `Scope.provide`.
- For `Effect.gen` with `this`, use `Effect.gen({ self: this }, ...)`.

## Recommended Implementation Order

### Phase 1: Document And Enforce The House Style

Files to modify:

- `packages/nikcli/AGENTS.md`
- Avoid creating a new `packages/nikcli/src/effect/README.md` unless `AGENTS.md` becomes too large or the team explicitly wants a separate guide.

Work:

- Add a short Effect v4 house-style section derived from the migration docs.
- Include service, schema, errors, runtime, and layer memoization conventions.
- Keep this docs-only at first; add a grep/check script only if the repo already has a lint/check pattern for architectural rules.

Verification:

- `bun run typecheck`
- Static grep for forbidden old APIs if a script is added.

### Phase 2: Tighten Existing Effect Infrastructure

Files to inspect/modify:

- `packages/nikcli/src/effect/runtime.ts`
- `packages/nikcli/src/effect/instance-scope.ts`
- `packages/nikcli/src/effect/with-instance.ts`
- `packages/nikcli/src/server/httpapi/bridge.ts`

Work:

- Ensure shared memoization is intentionally documented and tested.
- Add or adjust tests around `sharedMemoMap`, cancellation bridging, and `HttpApiBridge` context provisioning if gaps exist.
- Avoid changing behavior unless tests reveal drift.

Verification:

- `bun test test/session/*effect-service.test.ts test/tool/*effect-service.test.ts test/storage/effect-service.test.ts`
- `bun run typecheck`

### Phase 3: Convert High-Churn Schemas First

Files to inspect/modify opportunistically:

- `packages/nikcli/src/worktree/index.ts` as the reference pattern.
- `packages/nikcli/src/permission/schema.ts`

Work:

- For touched modules, define source-of-truth domain shapes with `Schema.Struct` and convert to Zod via `zodObject` only at legacy boundaries.
- Expand `src/util/effect-zod.ts` only when a new Schema construct appears in real code.

Verification:

- Relevant schema tests, e.g. `bun test test/permission/schema.test.ts test/loop/schema.test.ts test/interaction/spec.test.ts`

Files to inspect/modify:

### Phase 5: Continue HttpApi Migration Behind The Bridge

Files to inspect/modify:

- `packages/nikcli/src/server/routes/*.ts`
- `packages/nikcli/src/server/httpapi/*`

Verification:

- Relevant route tests.

### Phase 6: Use Effect Platform For New IO Services

Files to inspect/modify when adding new IO-heavy behavior:

- `packages/nikcli/src/file/*`
- `packages/nikcli/src/filesystem/index.ts`
- `packages/nikcli/src/git/index.ts`

Work:

Verification:

- Targeted tests for the modified service.
- `bun run typecheck`
- `bun test` when touching shared IO primitives.

## What Not To Take Yet

- Do not wholesale rewrite Hono routes to Effect HttpApi in one pass.
- Do not replace Zod globally; keep `effect-zod` as the bridge for Hono/OpenAPI/tool compatibility.
- Do not adopt `effect/unstable/sql`/`SqliteMigrator` unless database migration needs outgrow the current `src/database/migration.ts` runner and the database layer itself is moving to Effect SQL.
- Do not rework MCP around `effect/unstable/ai` until there is a concrete MCP/tooling feature to build.
- Do not churn stable legacy async modules solely for style; migrate when feature work or bugs touch them.

## Deliverable Recommendation

Start with Phase 1 plus a small Phase 2 test/docs pass. This gives the repo a verified Effect v4 migration contract before broad implementation work and keeps risk low because the current code already partially follows the opencode/effect-smol direction.
