# TUI Optimization Opportunities from Server Session Analysis

## Context

Explored two codebases:

1. **Server session routes** (`src/server/routes/session.ts` — 1527 lines, ~35 endpoints)
2. **TUI sync/context** (`src/cli/cmd/tui/context/sync.tsx` — 682 lines)

Goal: Identify TUI optimizations by comparing what the **server exposes** vs what the **TUI currently uses**.

---

## Identified Optimizations

### 1. **Lazy Message Loading** — High Impact

- **Server supports**: `limit` param on `GET /session/:id/message` (line 989-1003)
- **TUI currently**: Loads up to 100 messages via `session.sync()` (sync.tsx:624)
- **Optimization**: Implement virtual scrolling / incremental loading. Only fetch message **parts** (tool outputs, text) when a message is expanded, not upfront.

### 2. **Message Streaming via SSE** — Medium Impact

- **Server has**: `POST /session/:id/message` returns a streaming response (line 1172-1188)
- **TUI currently**: Uses `message.updated` WebSocket events to receive streaming
- **Optimization**: The WebSocket path is already used, but the TUI could optimize **render batching** — currently messages update on every token. Batch updates at 60ms intervals to reduce render cycles.

### 3. **Reactive Store Improvements** — High Impact

- **Current issue** (sync.tsx:362-379): When messages exceed 100, old ones are **dropped from memory** but still referenced in parts. This could cause stale UI.
- **Optimization**: Implement a proper **LRU cache** or **virtual list model** for messages instead of hard truncation at 100.

### 4. **Background Job Polling** — Medium Impact

- **Server has**: `GET /session/:id/background` for listing background jobs
- **TUI currently**: Uses `scheduleBackgroundRefresh` with 75ms debounce (sync.tsx:137-142)
- **Optimization**: Server already pushes `delegation.completed` events via WebSocket — TUI should **trust push over polling**. Only poll as fallback.

### 5. **Session Instructions Cache** — Low-Medium Impact

- **Server has**: `GET /session/:id/instructions` (line 246-298) — returns loaded instruction files
- **TUI currently**: Fetches instruction files per-session in sidebar (session/sidebar.tsx:23-38) — each SDK call awaits separately
- **Optimization**: Cache instruction file contents, only refresh when `Session.Event.ConfigUpdated` fires.

### 6. **Diff Lazy Loading** — Medium Impact

- **Server has**: `GET /session/:id/diff?messageID=...` (line 802-844) — per-message diff
- **TUI currently**: Loads all diffs upfront via `session.sync()` → `session.diff`
- **Optimization**: Load diffs **on demand** when user expands a message, not upfront.

### 7. **Part-Level Granularity** — Medium Impact

- **Server**: `PATCH /session/:id/message/:id/part/:partID` (line 1092-1140) for partial updates
- **TUI**: Receives `message.part.updated` events but may re-render entire message tree
- **Optimization**: Use Solid's fine-grained reactivity — parts are already stored separately (`store.part[messageID]`). Ensure renders are **part-level, not message-level**.

### 8. **Monitor Log Polling** — Medium Impact

- **Server has**: `GET /session/:id/monitor/:id/log?lines=200` (line 1455-1492)
- **TUI currently**: Uses `monitor.output` WebSocket events for live preview
- **Optimization**: For completed monitors, avoid fetching log unless user clicks to expand. Use preview from event payload instead.

### 9. **Session List Filtering on Server** — Low Impact

- **Server has**: Query params for filtering (`search`, `roots`, `start`, `limit`) (line 146-155)
- **TUI currently**: Loads all sessions (30-day window) and filters client-side
- **Optimization**: Use `limit=N` for initial load, load more on scroll.

### 10. **WebSocket Event Compression** — Medium Impact

- **Server**: Sends individual `message.part.updated` events per token for streaming
- **TUI sync**: Each event triggers `Binary.search` + store mutation + potential re-render
- **Optimization**: Consider **batching** multiple `part.updated` events into a single store update, applying changes in one `batch()` call.

### ✅ Render Batching (lines 127–159)

```typescript
const pendingPartUpdates = new Map<string, Map<string, unknown>>()
let batchTimer: ReturnType<typeof setTimeout> | null = null
const BATCH_INTERVAL_MS = 60

function scheduleBatchFlush() {
  if (batchTimer !== null) return
  batchTimer = setTimeout(() => {
    batchTimer = null
    const updates = pendingPartUpdates
    pendingPartUpdates = new Map()
    batch(() => {
      // apply all pending part updates in a single batch
    })
  }, BATCH_INTERVAL_MS)
}
```

### ✅ Message Truncation Fix (lines 395–412)

Old messages are removed from `store.message` but **parts are NOT deleted** — they remain cached for lazy loading. Comments in code: "Don't delete parts immediately — they may still be referenced / Parts will be garbage collected when session is unloaded."

```typescript
const [instructions] = createResource(
  () => props.sessionID,
  async (sessionID) => {
    const result = await sdk.client.session.instructions({ sessionID })
    return result.data ?? []
  },

```

**Opportunity**: Cache instruction file contents by file path, only refresh when `Session.Event.ConfigUpdated` fires. Instruction file contents are stable — they're loaded once and rarely change.
