# Built-in background browser control

## Plan review

The original proposal had the right package boundary and session-manager analogy, but two parts should change before implementation:

- Do **not** add an `ai-driver.ts` or invoke another LLM from inside the browser tool. The current nikcli agent already owns model selection, permissions, aborts, context, and tool iteration. A nested model loop would duplicate that machinery and make costs and failures harder to control.
- An in-memory `BrowserManager` is not enough for terminal-control-style background operation: separate CLI invocations need a persistent owner. Use a detached local daemon and authenticated loopback IPC so named Chromium sessions survive individual tool/CLI calls.
- Treat DOM snapshots as ephemeral control frames, not a faithful serialized browser. Element refs are scoped to a frame and must be rejected after navigation or refresh instead of pretending they are globally stable.
- Keep raw DOM, typed values, cookies, and recordings private by default. Expose compact semantic/accessibility state to the model and only persist evidence when recording is explicitly enabled.
- Remove Browser Use Cloud completely, but preserve a short compatibility window for obsolete browser config keys so existing user config does not fail to parse immediately.

## Recommended architecture

Create `@nikcli-ai/browser-control` as a sibling of `terminal-control`. It owns a local Playwright-managed Chromium process in a detached daemon. The daemon keeps one isolated `BrowserContext` per named session and one active page per session, while the current nikcli model drives deterministic actions through the existing `browser` tool. No Browser Use API key, Browser Use SDK, cloud session, proxy service, or second LLM loop is involved.

“Background” means `start` launches/attaches to the daemon and returns after the page is ready; Chromium and its contexts remain alive across later CLI/tool calls until `stop`, idle cleanup, or daemon shutdown.

## Implementation

### 1. Add the browser-control package

Create `packages/browser-control` with the monorepo package conventions:

- `package.json`, `tsconfig.json`, `README.md`, and `src/index.ts`; depend on pinned `playwright`/`playwright-core` and expose the `browser-control` binary.
- `src/protocol.ts`: versioned request/response types, action schemas, structured errors, session information, and daemon health/version negotiation.
- `src/daemon.ts` and `src/client.ts`: a single detached daemon bound to a random `127.0.0.1` port. Store PID, endpoint, and a random bearer token in a mode-0600 runtime file; serialize daemon startup with a lock; reject unauthenticated or version-mismatched clients; recover stale PID/runtime files; stop automatically after an idle timeout with no sessions.
- `src/manager.ts`: named session registry with `start/list/get/status/snapshot/action/stop/closeAll`. Replacing a same-named session must close its old context first. Limit concurrent sessions and serialize actions per session.
- `src/session.ts`: launch an isolated `BrowserContext`, maintain tabs/active page, apply viewport and timeouts, capture console/page errors, abort in-flight actions, close cleanly, and never attach to the user’s normal Chrome profile by default.
- `src/snapshot.ts`: produce a compact semantic frame containing `frameId`, URL, title, viewport, timestamp, focused element, and visible semantic nodes. Assign ephemeral refs only to actionable elements, keep the selector/locator map inside the daemon, and require matching `frameId` for ref actions so stale refs fail explicitly. Redact password values and avoid returning raw HTML.
- `src/recording.ts` and `src/evidence.ts`: explicit opt-in action/event recording with timestamps, markers, semantic frames, final screenshots, and optional Playwright video. Raw recordings stay excluded from bundles by default. Evidence bundles contain a hash-verified manifest, final PNG, semantic text/JSON, optional video/recording, and PR Markdown.
- `src/cli.ts`: `install`, `start`, `list`, `status`, `snapshot`, `goto`, `click`, `type`, `press`, `select`, `check`, `scroll`, `wait`, `tabs`, `screenshot`, `mark`, `stop`, `daemon stop`, `bundle`, and `install-skill`. Commands talk to the daemon instead of keeping process-local state. `install` explicitly installs Chromium; `start` reports an actionable error if no compatible executable is available rather than downloading silently.
- `skills/browser-control/SKILL.md`: teach agents to start a named background session, snapshot before acting, use `frameId` + refs, prefer deterministic waits over sleeps, request explicit authorization for consequential web actions, and always stop sessions.

Supported waits should include text, URL, selector, load state, and DOM/network stability with bounded timeouts. Supported tab operations should include list, new, switch, and close. Every mutating action should return updated session metadata and a refreshed compact frame; screenshots remain explicit or attached where useful rather than being persisted on every action.

### 2. Integrate the daemon into nikcli

Replace the Browser Use Cloud adapter while retaining the public tool ID `browser`:

- Rewrite `packages/nikcli/src/browser/browser.ts` as a thin lifecycle wrapper around `@nikcli-ai/browser-control`. Derive collision-safe daemon session names from nikcli session IDs, expose status/messages from local action history, and close owned sessions during `Instance` disposal without killing unrelated CLI sessions.
- Rewrite `packages/nikcli/src/tool/browser.ts` to expose direct actions: `start`, `status`, `snapshot`, `navigate`, `click`, `type`, `press`, `select`, `check`, `scroll`, `wait`, `tabs`, `screenshot`, and `stop`. Remove `task`, `model`, `maxCostUsd`, `profileId`, and proxy fields. The outer/current agent performs the reasoning over repeated tool calls.
- Keep permission checks in nikcli: include action and target origin/ref in permission patterns, never include typed secret text in metadata/history, and preserve the existing policy that sending, purchasing, uploading, deleting, signing in, or transmitting sensitive data needs exact user authorization.
- Attach local PNGs as data URLs using the same message-part pattern as `computer`; metadata should use `surface: "browser"`, `provider: "local"`, session status, URL/title, and current `frameId`. Do not fabricate a `liveUrl`; status/snapshot and screenshots are the observability surface.
- Replace `packages/nikcli/src/tool/browser.txt` with local-browser instructions, including prompt-injection warnings because page text is untrusted.
- Add `@nikcli-ai/browser-control` to `packages/nikcli/package.json` and remove `browser-use-sdk`. Update `bun.lock` with Bun.

### 3. Migrate config and UI safely

- Replace the Browser Use-specific schema in `packages/nikcli/src/config/config.ts` with local settings such as `headless`, viewport width/height, executable path/channel, action timeout, daemon idle timeout, and optional explicit profile/storage directory. Accept legacy `model` and `max_cost_usd` fields as deprecated no-ops for one compatibility cycle, with a warning, rather than making existing config unreadable.
- Remove all `BROWSER_USE_API_KEY` and auth-vault lookup/setup paths. Do not delete existing user auth entries automatically; simply stop reading them.
- Update Browser Use naming/setup assumptions in `packages/nikcli/src/cli/cmd/tui/routes/session/index.tsx`, `packages/nikcli/src/cli/cmd/tui/component/dialog-browser-use.tsx`, `packages/nikcli/src/cli/cmd/tui/component/dialog-onboarding.tsx`, `packages/nikcli/src/cli/cmd/tui/feature-plugins/browser/index.tsx`, `packages/desktop/src/shell.tsx`, `packages/ui/src/components/message-part.tsx`, and `packages/nikcli/src/flag/flag.ts`. Show local session state, URL/title, action summary, screenshots, and install diagnostics instead of requesting a cloud key or embedding a remote live preview.
- Rename browser config schema/docs to local terminology and regenerate `packages/sdk/openapi.json` plus `packages/sdk/js/src/v2/gen/**` using `packages/sdk/js/script/build.ts`, because the config contract changes.

### 4. Tests and failure handling

Add focused tests rather than relying on public websites:

- `packages/browser-control/test/snapshot.test.ts`: deterministic semantic output, actionable refs, password redaction, hidden-node filtering, stale-frame rejection, and ref refresh after DOM mutation/navigation.
- `packages/browser-control/test/session.test.ts`: local Bun HTTP fixture covering navigation, click/type/press/select/check/scroll, tabs, waits, screenshot, console/page errors, and cleanup.
- `packages/browser-control/test/daemon.test.ts`: separate client processes share a named background session; startup races, stale runtime files, authentication, idle shutdown, and explicit daemon stop behave correctly.
- `packages/browser-control/test/recording.test.ts` and `evidence.test.ts`: opt-in capture, redaction defaults, checksums, raw-recording exclusion, and video finalization on context close.
- Update `packages/nikcli/test/tool/registry-effect-service.test.ts` to assert local availability rather than Browser Use key detection, and add browser tool tests using an injectable/fake browser-control client so normal unit tests do not launch Chromium.
- Add UI/component assertions for the local labels and removal of cloud-key setup where existing test infrastructure permits.

Handle missing Chromium, daemon crashes, page crashes, action timeout, stale refs, and aborted tool calls with concise recoverable errors. Ensure daemon/browser/context/process cleanup runs on test teardown and nikcli instance disposal.
