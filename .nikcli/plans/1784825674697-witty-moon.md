# Piano: Wake-Dedup per eliminare la "Parent ↔ child wake ordering race"

> **Status**: Level 1 implemented (2026-07-23) · Levels 2–3 still out of scope
> **Scopo**: risolvere la root cause del duplicate-processing che impatta 3 sistemi contemporaneamente (delegation, loop, mission) e il TUI consumer, riutilizzando primitive esistenti.

---

## 1. Perché questo piano

L'analisi di concorrenza (4 agent in parallelo) ha identificato che il "Parent ↔ child wake ordering race" è la radice sistemica di:

- `delegation.completed` pubblicato due volte quando `cancel()` + `scheduleForcedFinalize()` concorrenti entrambi passano il guard `persisted.status !== "running"` prima che l'altro scriva (`delegation/manager.ts:513-550`).
- Reconciler `reconcileInterrupted` (`background/run.ts:571-586`) che può ri-emettere `delegation.completed` su cold-start.
- `Loop RunFinished` pubblicato da 4 siti distinti (`loop/engine.ts:402, 542, 668` + via `Finalize`) senza dedup.
- `Mission Finished` pubblicato da 6+ siti (`mission/orchestrator.ts:394, 425, 451, 485, 544, 591`).
- TUI worker reconnect su 250 ms (`cli/cmd/tui/worker.ts:81-99`) — eventi perduti senza replay.
- Nessun `Last-Event-ID` server-side (`grep Last-Event-ID` → 0 risultati).

**Impatto del fix**: elimina computazione duplicata (delegation/loop/mission/TUI), previene context burn, è **additivo** (nessuna migrazione di schema), riusa primitive esistenti.

**Cosa NON fa questo piano**: nessuna modifica al core delegation manager (no migration); nessuna modifica a Loop/Mission engines (sistemati indirettamente dal TUI); nessun nuovo protocollo.

---

## 2. Strategia

Tre livelli di dedup, dal più economico al più robusto. **Si applica solo il livello 1 nel primo passaggio**; i livelli 2 e 3 sono incrementali solo se servono.

### Livello 1 — Consumer-side envelope dedup (QUESTA IMPLEMENTAZIONE)

Un LRU a monte di tutti gli handler TUI identifica eventi già processati. Reusa la primitiva canonica del codebase.

### Livello 2 — Extended server-side event id (follow-up opzionale)

Aggiungere `id:` al payload SSE + `Last-Event-ID` header al reconnect. Richiede modifica a `server/server.ts:1008-1080` e a `cli/cmd/tui/worker.ts:47-109`.

### Livello 3 — Producer-side atomic finalize guard (follow-up opzionale)

In `delegation/manager.ts:513` aggiungere un `Map<delegationID, Promise>` (single-flight) per garantire che `finalize()` venga chiamato una sola volta anche con 3 trigger concorrenti.

## 3. File da modificare (Livello 1, solo)

### 3.1 `packages/nikcli/src/cli/cmd/tui/util/wake-dedup.ts` — **NUOVO**, ~60 righe

Crea un nuovo helper che wrappa `createLru` con una chiave derivata dall'evento:

```ts
import { createLru, type Lru } from "../util/lru-cache"

export type WakeDedupOptions = {
  /** Cap su envelopes tracciate. Default 256 — sufficiente per retry-burst + reconnect storms. */
  maxEntries?: number
  /** TTL di una entry. Default 60_000 ms — copre qualunque gap di reconnect plausibile. */
  ttlMs?: number
}

export type WakeKeyExtractor = (envelope: { type?: string; properties?: unknown }) => string | undefined

/**
 * Restituisce `true` la prima volta che una data chiave viene vista, `false` per le successive.
 * Per eventi senza chiave estratta, ritorna sempre `true` (non-blocking).
 */
export function createWakeDedup(extract: WakeKeyExtractor, options: WakeDedupOptions = {}) {
  const lru: Lru = createLru({ maxEntries: options.maxEntries ?? 256, ttlMs: options.ttlMs ?? 60_000 })
  return {
    shouldProcess(envelope: { type?: string; properties?: unknown }): boolean {
      const key = extract(envelope)
      if (key === undefined) return true
      if (lru.has(key)) return false
      lru.touch(key)
      lru.evictOverflow() // safety
      return true
    },
    forget(key: string): void {
      lru.forget(key)
    },
    size(): number {
      return lru.size
    },
  }
}
```

**Perché un nuovo helper**: la primitiva LRU esiste (`cli/cmd/tui/util/lru-cache.ts:1-87`) ed è giustamente "data-structure only". Wake-dedup aggiunge la _semantica_ "key extraction + default-allow policy" che non appartiene al core LRU.

### 3.3 `packages/nikcli/src/cli/cmd/tui/context/sync.tsx` — MODIFICA incrementale al `scheduleBackgroundRefresh`, ~10 righe

Estende la debounce esistente di 75 ms (`sync.tsx:182-191`) per tracciare l'ultimo `delegationID` processato per `sessionID`, così una sequenza di `delegation.completed` + 12 `message.part.updated` che riferiscono lo stesso child non genera doppio `refreshBackgroundJobs`.

```ts
// aggiungi subito sopra scheduleBackgroundRefresh (~line 181):
const lastDelegationBySession = new Map<string, string>()

// sostituisci la firma di scheduleBackgroundRefresh:
function scheduleBackgroundRefresh(sessionID?: string, delegationID?: string) {
  if (!sessionID) return
  if (delegationID && lastDelegationBySession.get(sessionID) === delegationID) {
    // stessa delegatione: lascia che il debounce esistente consolidi
    const existing = backgroundRefreshTimers.get(sessionID)
    if (existing) {
      clearTimeout(existing)
    }
  } else {
    if (delegationID) lastDelegationBySession.set(sessionID, delegationID)
  }
  const existing = backgroundRefreshTimers.get(sessionID)
  if (existing) clearTimeout(existing)
  const timer = setTimeout(() => {
    backgroundRefreshTimers.delete(sessionID)
    void refreshBackgroundJobs(sessionID).catch(() => {})
  }, 75)
  backgroundRefreshTimers.set(sessionID, timer)
}
```

E aggiorna il call-site `sync.tsx:495-498` (`delegation.completed` handler) per passare il `delegationID`:

```ts
case "delegation.completed":
  scheduleBackgroundRefresh(event.properties.parentSessionID, event.properties.delegationID)
  break
```

E `sync.tsx:461-493` (`message.part.updated` handler) — non serve passare `delegationID` da ogni `message.part.updated` (non è noto in quel momento); il debounce 75 ms esistente + LRU envelope sopra sono sufficienti.

### 5.3 Metriche di successo

- **Prima**: stesso `delegationID` può apparire ≥2 volte nei log di wake sotto cancel-then-finalize race.
- **Dopo**: ogni `delegationID` appare esattamente 1 volta nel log di wake.

- **Memoria**: bounded a `maxEntries × 32 bytes ≈ 8 KB` per la struttura LRU.

## 7. Rischi e limiti noti

| Rischio                                                                        | Mitigazione                                                                                                           |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| LRU pieno con keys ad alta cardinalità spreca memoria                          | `maxEntries: 256` + `evictOverflow()` su ogni `touch`; su 256 entries × ~32 bytes ≈ 8 KB.                             |
| Extractor non copre un nuovo evento, evento duplicato sfugge                   | Default-allow (`return undefined` → passa); la dedup funzionale esistente in `sync.tsx` resta come safety net.        |
| TUI reconnettito durante un flood di eventi → chiavi scadono prima dell'arrivo | TTL 60 s; se la reconnect gap supera i 60 s non c'è degrado aggiuntivo rispetto allo stato attuale (oggi zero dedup). |
| Modifica rompe il batching da 16 ms in `flush()`                               | Il filtro è fatto PRIMA della `batch()` e con costo O(n) trascurabile; nessuna modifica al timer 16 ms.               |
| Esposizione di `lastDelegationBySession` come Map globale (memory growth)      | Chiavi sono `sessionID`; entrate dimenticate su `session.deleted` handler esistente (`sync.tsx:344`).                 |
