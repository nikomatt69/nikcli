# Piano: Migliorare workspace/, worktree/, sync/, sandbox/

## Analisi di 5 agenti esplorativi

### output dei 5 agenti (sommario)

**Agent 1 - workspace/**: Fornisce ambienti di esecuzione isolati (worktree locali o container) con sync event via SSE. SQLite + Map per stato, in-memory Map per sync controller. Debolezze: stato globale mutabile, no cleanup su exit, fragile URL matching, no health checks per worktree, race conditions nello sync.

**Agent 2 - worktree/**: Gestione git worktree (create/remove/reset) in un singolo file. Monorepo support via symlink node_modules. Debolezze: operazioni non atomiche, listing duplicato, no cleanup su failure, symlink error swallowed, no list API.

**Agent 3 - sync/**: Event sourcing pattern (emit/replay/projector) completamente **disconnesso** - non importato da nessuno nel codebase. storage basato su file JSON. Debolezze: zero usage, no schema validation on emit, no pagination, no compaction, no atomicity.

**Agent 4 - sandbox/**: Ref (local/workspace) + State (local/worktree/container) + Handle. Registry per risolvere Ref a Handle. Debolezze: no test coverage, Handle non validabile via Zod, no lifecycle management, no caching, no logging.

**Agent 5 - cross-module**: workspace↔sandbox duplicazione (SandboxRegistry.resolve ≈ Workspace.target), SyncEvento completamente unused, stato storage inconsistente (SQLite vs in-memory vs file JSON), Target resolution inconsistente.

## Fix proposti

### FASE 1: Quick wins stabilita (basso rischio)

#### 1.1 Worktree: estrarre listWorktrees() condivisa

File: `src/worktree/index.ts`

- Il parsing di `git worktree list --porcelain` e duplicato in `remove()` e `reset()` (circa 80 righe ciascuno).
- Estrarre una funzione interna `listWorktrees(directory: string): Promise<Worktree.Info[]>` che ritorna tutte le info del worktree corrente + worktrees.
- Riusarla in remove e reset invece del parsing inline.
- Aggiungere una `Worktree.list(): Promise<Info[]>` pubblica (via fn()) che sfrutta questa funzione.

#### 1.2 Worktree: cleanup on create failure

File: `src/worktree/index.ts` - funzione `create()`

- Dopo `git worktree add` riuscito, se symlink o startCommand falliscono, il worktree rimane orphaned.
- Aggiungere blocco try/catch: se operazioni post-creation falliscono, chiamare `git worktree remove <directory>` come cleanup.
- Loggare il fallimento con `Log.create({ service: "worktree" })`.

#### 1.3 Workspace: logging in SandboxRegistry

File: `src/sandbox/registry.ts`

- Aggiungere `const log = Log.create({ service: "sandbox.registry" })` all'inizio.
- Loggare resolve/start/error per ogni operazione.
- Cambiare `throw new Error(...)` in `NamedError` pattern.

#### 1.4 Workspace: rendere event limit configurabile

File: `src/workspace/db.ts` - `appendEvent()`

- L'hardcoded 200-event limit in `WorkspaceDB.appendEvent()` dovrebbe essere configurabile via workspace config o global config.
- Aggiungere opzione `eventLimit?: number` nello stato workspace e usarla in appendEvent.
- Default: 200 per backward compat.

#### 1.5 Worktree: parallel reset per submodules

File: `src/worktree/index.ts` - funzione `reset()`

- Le operazioni submodule sono sequential: `update`, `reset --recursive`, `clean -fdx`.
- Cambiare in `Promise.allSettled()` per fail-fast su mixed results.

### FASE 2: Integrare Sync con workspace event loop

Il modulo `src/sync/` non e usato ma ha un pattern event-sourcing interessante. L'obiettivo e integrarlo con il workspace event mirroring invece di rimuoverlo.

#### 2.1 Sync: sostituire file JSON storage con WorkspaceDB

File: `src/sync/storage.ts` (nuovo) o modificare `src/sync/index.ts`

- Il workspace event loop in `src/workspace/index.ts` gia memorizza eventi in `WorkspaceDB.events` (200 limit).
- Integrare `SyncStorage` per usare WorkspaceDB invece di file JSON separati:
- events per aggregate洗脸 da WorkspaceDB.events filtrato per tipo
- sequence洗干净 da workspace state (ultimo seq per aggregate)

#### 2.2 Sync: definire i tipi eventi per RESTORE_EVENT_TYPES

File: `src/sync/index.ts` - SyncEvent registry

- Registrare gli eventi in `RESTORE_EVENT_TYPES` come `SyncEvent.define()`:
  - `session.created`, `session.updated`, `session.deleted`
  - `session.status`, `session.idle`
  - `permission.asked`, `permission.replied`
  - `question.asked`, `question.replied`, `question.rejected`
- Questo abilita `Sync.getEvents(projectID, "session")` per replay.

#### 2.3 Sync: validation on emit

File: `src/sync/index.ts` - funzione `Sync.emit()`

- Aggiungere `eventDef.schema.parse(data)` per validare l'event data prima di salvare.
- Questo era il bug principale: emit non validava lo schema.

#### 2.4 Sync: compaction

File: `src/sync/index.ts` - `SyncStorage.appendEvent()`

- Aggiungere compaction: quando gli eventi per un aggregate superano 1000, mantenere solo gli ultimi 500.
- Questo previene crescita illimitata dei file events.

#### 2.5 Sync: atomic write

File: `src/sync/index.ts` - `SyncStorage.appendEvent()`

- Attualmente due write separate (events + sequence) senza atomicita.
- Usare write pattern: scrivere su file temp, poi rename (atomic su filesystem).

### FASE 3: Workspace global state + cleanup

#### 3.1 Workspace: global state cleanup

File: `src/workspace/index.ts`

- `syncControllers` e `connectionStatuses` sono Maps a livello di modulo che non vengono puliti su process exit.
- Aggiungere `process.on("beforeExit" | "SIGTERM", () => stopAllSyncing())`.
- Per connectionStatuses: usare FinalizationRegistry per cleanup automatico.

#### 3.2 Workspace: race condition fix in startSpaceSync

File: `src/workspace/index.ts` - `startSpaceSync()`

- Il check `if (syncControllers.has(space.id)) return` non e atomico.
- Usare un `Set<string>` "starting" come mutex locale.

#### 3.3 Workspace: fragile URL heuristic fix

File: `src/workspace/session-proxy-middleware.ts`

- Il regex `/session/ses_[^/]+` e fragile.
- Aggiungere un middleware che mette workspaceID nel context prima delle route.

#### 3.4 Workspace: health check per worktree

File: `src/workspace/adaptors/worktree.ts`

- Aggiungere health check per worktree: verify `.git` exists e branch matches.

### FASE 4: Sandbox improvements

#### 4.1 Sandbox: caching in resolve

File: `src/sandbox/registry.ts`

- `SandboxRegistry.resolve()` fetcha workspace da storage ad ogni chiamata.
- Aggiungere LRU cache con TTL 30s per workspace lookup.

#### 4.2 Sandbox: Handle as validatable schema

File: `src/sandbox/types.ts`

- `Sandbox.Handle` e un plain TypeScript interface non validabile.
- Aggiungere `Sandbox.Handle` come Zod schema che include le parti serializzabili + un metodo schema pattern.
- Per il metodo `target()`, usare un `_targetFn: () => Promise<Target>` campo o un pattern diverso.

#### 4.3 Sandbox: deduplicare con Workspace.target()

File: `src/workspace/index.ts` - `sandbox()` + `src/sandbox/registry.ts`

- `Workspace.sandbox()` chiama `SandboxRegistry.resolve()` che duplica `Workspace.target()`.
- Unificare: `Workspace.sandbox()` restituisce direttamente un Handle senza passare da SandboxRegistry.
- Rimuovere o semplificare SandboxRegistry per essere solo un factory di Ref, non di Handle.

#### 4.4 Sandbox: add lifecycle management

File: `src/sandbox/registry.ts` (o nuovo `src/sandbox/lifecycle.ts`)

- Aggiungere `Sandbox.create(config)`, `Sandbox.delete(handle)`, `Sandbox.start(handle)`, `Sandbox.stop(handle)`.
- Delegare a Workspace.create/remove e adaptor corrispondenti.
- Questo centralizza la logica che oggi e sparsa su Workspace e adaptors.
