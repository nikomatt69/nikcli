# Plan: Vercel Sandbox setup for nikcli

## Recommendation

Use `packages/nikcli/script/vercel-sandbox-smoke.ts` for the first Vercel Sandbox verification script, not `packages/nikcli/src/sandbox`.

`src/sandbox` already models Nikcli's own workspace sandbox abstraction (`local`, `worktree`, `container`) through `SandboxRegistry` and workspace adaptors. For this request, we only need a setup/smoke script that proves the Vercel SDK can create a remote microVM, run code, capture stdout/stderr, and stop the sandbox. Keeping it under `script/` avoids mixing a Vercel experiment into the runtime abstraction before we decide to productize it.

Do not switch the initial implementation to `@cloudflare/sandbox`. Cloudflare Sandbox is promising for a production, Cloudflare-native backend, but it is a Worker + Durable Object + Cloudflare Containers integration: local testing requires Docker, production requires Wrangler deployment/provisioning, and the SDK is currently beta. Vercel Sandbox is a smaller first step for this request because it can be verified from one local Bun script after `vercel link` / `vercel env pull`.

Cloudflare should be revisited if the goal changes from "verify remote sandbox execution from nikcli" to "ship a hosted sandbox service on our Cloudflare infrastructure".

## Cloudflare comparison

- The repo already has Cloudflare deployment surfaces (`sst.config.ts`, `packages/cloud`, `packages/companion`, `packages/slack`, `packages/web`), so Cloudflare is strategically plausible later.
- `@cloudflare/sandbox` runs from Workers applications and binds a `Sandbox` Durable Object backed by a container image in `wrangler.toml` / `wrangler.jsonc`.
- Local development needs Docker running and `wrangler dev`; first local run builds a container image, and production deploys/provisions containers with `wrangler deploy`.
- It is better suited for a server/API endpoint that brokers sandbox requests than for a simple CLI smoke script inside `packages/nikcli`.
- If selected later, implement it as a new Worker-facing package or service first, then add a `cloudflare` workspace adaptor to `packages/nikcli/src/workspace/adaptors` only after the API shape is stable.

## Files to modify

- `packages/nikcli/package.json`
  - Add `@vercel/sandbox` to dependencies via Bun.
  - Add a package script such as `sandbox:vercel` that runs the smoke script.
- `bun.lock`
  - Update through `bun add`, not manually.
- `packages/nikcli/script/vercel-sandbox-smoke.ts`
  - New executable Bun/TypeScript smoke script.
- `.gitignore`
  - Add `.vercel` so `vercel link` local project metadata is not committed. Existing ignore rules already cover `.env.local`.

## Setup steps

1. Check/install the Vercel CLI:
   - Verify with `vercel --version`.
   - If missing or outdated, run `npm i -g vercel`.
2. Install Vercel agent support for this environment:
   - Since this is Nikcli rather than Claude Code/Cursor, run `npx skills add vercel-labs/agent-skills`.
   - Do not run `npx plugins add vercel/vercel-plugin` unless the user is actually executing from Claude Code or Cursor.
3. Install the SDK from the package directory:
   - `bun add @vercel/sandbox` in `packages/nikcli`.
4. Link and pull credentials from `packages/nikcli`:
   - `vercel link`
   - `vercel env pull .env.local`
   - This should provide `VERCEL_OIDC_TOKEN`; it expires after about 12 hours, so re-run `vercel env pull .env.local` on auth failures.

## Smoke script design

Create `packages/nikcli/script/vercel-sandbox-smoke.ts` with this behavior:

- Import `Sandbox` from `@vercel/sandbox`.
- Create a sandbox with `runtime: "node24"` and a short timeout, for example 2 minutes.
- Write a small JavaScript file into `/vercel/sandbox`, for example `verify.js`, using `sandbox.fs.writeFile` or `sandbox.writeFiles`.
- Run the file with `sandbox.runCommand({ cmd: "node", args: ["verify.js"], cwd: "/vercel/sandbox" })`.
- Capture `exitCode`, `await result.stdout()`, and `await result.stderr()`.
- Print a compact local summary containing the sandbox ID, command ID, exit code, stdout, and stderr.
- Throw or set `process.exitCode = 1` when the sandbox command exits non-zero.
- Always stop the sandbox in `finally` with `await sandbox.stop({ blocking: true })` to avoid unnecessary cost.

Add this package script:

```json
"sandbox:vercel": "bun run script/vercel-sandbox-smoke.ts"
```

## Verification

Run from `packages/nikcli`:

1. `vercel --version`
2. `bun run sandbox:vercel`
   - Expected output includes `Hello from Vercel Sandbox`, a Node version, sandbox ID, command ID, and exit code `0`.
3. `bun run typecheck`
4. Optional focused regression check: `bun test test/sandbox/registry.test.ts`

## Later integration path

If we later want Vercel Sandbox to become a first-class Nikcli workspace backend, then expand the existing runtime abstraction instead of only using the smoke script. That would require adding a `vercel` config/state variant in `src/workspace/config.ts`, `src/sandbox/types.ts`, `src/sandbox/registry.ts`, and a Vercel adaptor in `src/workspace/adaptors/index.ts`, plus tests. That is intentionally out of scope for the initial setup.
