# Nikcli Package Architecture Analysis

## Overview

This document summarizes the comprehensive analysis of the nikcli monorepo, covering core architecture, TUI components, SDK patterns, and plugin systems.

---

## 1. Core Architecture (`packages/nikcli`)

### High-Level Structure

```
packages/nikcli/
├── src/
│   ├── cli/          # CLI entry point & commands
│   │   ├── cmd/      # Command definitions
│   │   │   ├── tui/  # Terminal UI (SolidJS)
│   │   │   └── ...
│   ├── server/       # Hono HTTP server
│   ├── agent/        # Agent definitions & runtime
│   ├── tool/         # Tool registry & definitions
│   ├── session/      # Session & message management
│   ├── storage/      # File-based persistence
│   └── ...
├── package.json
└── tsconfig.json
```

**Entry Point**: `src/cli/cli.ts` - Bun CLI entry with command routing

### Agent System (`src/agent/`)

**Key File**: `src/agent/agent.ts`

- Predefined agents: `ralph`, `build`, `plan`, `explore`, `planner`, `code-reviewer`, `debugger`, `test-runner`, `refactor`, `delegator`
- Zod schemas for validation: `Agent.Info`, `Agent.Config`, `Agent.tool()`
- Effect-based dependency injection via `App.provide()`
- Agent names use kebab-case (e.g., `fast-explore`)

### Tool System (`src/tool/`)

**Key Pattern**: `Tool.define(name, config | executeFn)`

```typescript
export const MyTool = Tool.define("my-tool", {
  description: "Description",
  parameters: z.object({ ... }),
  execute: async (args, ctx) => ({ title, metadata, output })
})
```

- All inputs validated with Zod schemas
- Context includes: sessionID, messageID, agent, abort, ask
- Registry at `src/tool/registry.ts`

### Session/Message System (`src/session/`)

- **ID Generation**: `Identifier.descending("session")`, `Identifier.ascending("message")`
- **Session IDs**: Descending for natural ordering
- **Message IDs**: Ascending for chronological ordering
- **Storage Keys**: `["session", projectID, sessionID]`
- Schemas: `Session.Info`, `Message.Info`, `Message.Part.Info`

### Server (`src/server/server.ts`)

- **Framework**: Hono HTTP server
- **Communication**: Server-Sent Events (SSE) for real-time updates
- **API Structure**: REST endpoints + SSE streams
- Routes organized by domain

### Storage (`src/storage/storage.ts`)

- **Pattern**: In-memory cache + file-based JSON persistence
- **Namespace**: `Storage.read()`, `Storage.write()`, `Storage.update()`, `Storage.remove()`
- **Key Format**: `["collection", id, ...]` hierarchical
- **Error Handling**: `Storage.NotFoundError` for missing resources

## 2. TUI Components (`src/cli/cmd/tui/`)

### Structure

```
src/cli/cmd/tui/
├── index.tsx              # Main TUI entry
├── routes/                # Route components
│   ├── home/
│   ├── session/
│   │   ├── index.tsx      # Session list
│   │   ├── [id].tsx       # Session detail
│   │   └── dialog/        # Dialog components
│   └── ...
├── component/             # Reusable components
│   ├── input/
│   ├── dialog/
│   └── ...
├── provider/              # Context providers
└── state/                 # State management
```

### State Management

- **Framework**: SolidJS with reactive primitives
- **Provider Hierarchy**: App → SDK → Session → UI state
- **SDK Integration**: SDK client injected via context

### Dialog System

- Route-based dialogs at `routes/session/dialog/`
- Types: `Dialog.bg-agents.tsx`, `Dialog.edit.tsx`, etc.
- Interaction patterns: Forms, inputs, action buttons

### Backend Communication

- SDK client connects to server via `@nikcli-ai/sdk`
- Real-time updates via SSE subscriptions
- Command execution through tool invocations

## 3. SDK Architecture (`packages/sdk/`)

### Structure

```
packages/sdk/
├── js/                    # JavaScript SDK
│   ├── src/               # Source (used directly)
│   └── script/            # Code generation
│       └── build.ts       # OpenAPI → TypeScript client
├── ts/                    # TypeScript SDK (generated)
└── package.json
```

### Code Generation Pipeline

**Build Script**: `packages/sdk/js/script/build.ts`

1. Fetch OpenAPI spec from running nikcli server
2. Generate TypeScript types & client
3. Copy to `packages/sdk/ts/`

### API Namespaces

- `Sessions`: CRUD for sessions
- `Messages`: Message creation & retrieval
- `Agents`: Agent operations
- `Tools`: Tool listings
- `Storage`: Storage operations

### Type Sharing Flow

```
Zod Schemas (nikcli) → OpenAPI Spec → Generated SDK Types
```

## 4. Plugin System (`packages/plugin/`)

### Server Plugins

**Definition**: `Plugin = (input, options) => Promise<Hooks>`

**Hook Types**:

- `onServerStart`: Server initialization
- `onSessionCreate`: Session creation
- `onMessageCreate`: Message creation
- `onToolRegister`: Tool registration
- `onAgentRun`: Agent execution
- `onStorageRead/Write`: Storage operations

**Location**: `packages/plugin/src/index.ts`

### TUI Plugins

- Plugin API for extending TUI components
- Component registration system
- Route extensions

### Loading System

1. Plugins discovered from configuration
2. Initialized in order (dependencies resolved)
3. Hooks registered with core system
4. Active throughout server lifecycle

## 5. Remote Execution (`packages/remote/`)

- Plugin-based remote execution system
- Protocol for distributed agent execution
- Connection management and fallback

## Key Patterns Summary

| Pattern          | Implementation                            |
| ---------------- | ----------------------------------------- |
| Tool Definition  | `Tool.define(name, config)`               |
| Agent Names      | kebab-case (`fast-explore`)               |
| IDs              | Descending (session), Ascending (message) |
| Storage Keys     | `["collection", id, ...]`                 |
| Error Handling   | NamedError, Storage.NotFoundError         |
| Logging          | `Log.create({ service: "name" })`         |
| Input Validation | Zod schemas                               |
| SDK Generation   | OpenAPI spec → TypeScript                 |
