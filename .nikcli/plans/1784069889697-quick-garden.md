# Plan: Make `packages/nikcli` Production-Perfect

## Objective

Turn the current Bun/TypeScript AI agent platform into a bounded, observable, secure, and verifiably reliable product without a risky rewrite. “Perfect” means: deterministic lifecycle ownership, truthful persistence/sync guarantees, bounded resource usage, explicit trust boundaries, consistent API behavior, and release gates that prove the critical paths.

## Scope and principles

- Work only in `packages/nikcli` and the directly generated SDK artifacts required by server contract changes.
- Preserve current CLI/TUI/API behavior; ship risky changes behind existing experimental/config flags until soak evidence justifies default-on.
- Prefer small vertical changes with focused failure tests over broad refactors.
- Treat `src/session`, `src/storage`, `src/sync`, `src/server`, `src/workspace`, `src/tool`, and `src/effect` as the critical path.
- Do not rotate/delete any credential automatically; first audit repository/config history and require the owner to revoke any real exposed credential.

## Phase 0 — Baseline and safety gates

1. Record the current branch, clean/dirty state, Bun version, test/typecheck/build/lint results, and the generated HTTP API inventory.
2. Add a repeatable verification command or CI job that runs:
   - `bun run typecheck`
   - `bun test`
   - `bun run lint`
   - `bun run build`
   - focused server/session/storage/sync/tool tests
3. Define release gates: no type errors, no lint errors, no unbounded output regressions, no leaked listeners/timers after disposal, deterministic cancellation, and compatibility tests for Hono plus HttpApi routes.
4. Capture performance baselines for startup, first model token, large-session prompt construction, tool output, and memory under long-running SSE/PTY sessions.

## Phase 1 — Security and trust boundaries (highest risk)

1. Audit `nikcli.json`, `.nikcli`, test fixtures, examples, and Git history for tokens, API keys, passwords, and bearer credentials. Classify intentional fixtures versus real secrets; revoke/rotate real credentials outside the code change, then replace them with environment-backed test values.
2. Review server authentication and authorization in `src/server/server.ts`, `src/server/httpapi/*`, `src/server/routes/*`, `src/auth`, and mobile/companion routes. Ensure every non-loopback exposure has explicit auth, safe CORS, bounded request bodies, and consistent error responses.
3. Harden dynamic code loading in `src/tool/registry.ts`, `src/plugin`, `src/skill`, and config directory discovery: canonicalize paths, reject traversal/symlink escapes where appropriate, record origin, and make trust/permission policy explicit before executing user/plugin code.
4. Audit command and process boundaries in `src/tool/bash.ts`, `src/pty`, `src/lsp`, `src/git`, and all `Bun.spawn`/`child_process` callsites. Enforce abort propagation, timeout, output limits, exit-status handling, and safe environment inheritance.
5. Add negative tests for unauthenticated HTTP access, origin/CORS failures, path traversal, untrusted plugin loading, oversized bodies, command timeout, command cancellation, and secret redaction in logs/errors.

## Phase 2 — Session lifecycle and cancellation correctness

1. Establish one owner for per-session execution and abort state across `src/session/prompt.ts`, `src/session/processor.ts`, `src/session/runner.ts`, `src/session/status.ts`, `src/question`, `src/permission`, and server session routes.
2. Make every spawned fiber, provider stream, tool execution, shell process, question, permission request, and retry attempt attach to the session scope and dispose on completion, cancellation, error, and instance shutdown.
3. Preserve the runner state-machine guarantees (`Idle`, `Running`, `Shell`, `ShellThenRun`) while making cancellation idempotent and ensuring callers receive the correct typed cancellation result.
4. Add deterministic tests for concurrent prompts, shell-then-run, repeated cancel, cancel during provider headers/body/tool/question/permission, retry cancellation, disposal during active work, and no work after cancellation.
5. Add end-to-end session tests that assert exactly one terminal assistant state and no orphaned status/event/message parts.

## Phase 3 — Truthful persistence and synchronization

1. Review `src/storage/storage.ts` and `src/storage/effect.ts`: document the actual atomicity model, acquire locks in one consistent order, ensure parent directories exist, invalidate all affected cache entries on transactions/removals, and avoid claiming rollback if partial filesystem writes remain possible.
2. Add failure-injection tests for write/update/remove/transaction failures, concurrent readers/writers, cache staleness, migration interruption, malformed JSON, missing parents, and process restart recovery.
3. Audit `src/sync`, `src/workspace`, `src/workspace/projection.ts`, `src/workspace/db.ts`, and remote sync adapters for sequence allocation, duplicate delivery, replay ordering, outbox acknowledgement, reconnect, and idempotent projection updates.
4. Define the sync invariant explicitly: event sequence is monotonic, replay is repeatable, applying the same event twice is safe, and a reconnect cannot lose or reorder committed events. Encode each invariant in tests.
5. Only after these tests pass, complete the Effect event-log/`Sync.Service` migration described by `specs/effect/sync-service.md`; keep legacy Hono sync/SSE paths until parity tests pass.

## Phase 4 — Bounded resources and transport cleanup

1. Cap retained output in `src/tool/bash.ts` itself, not only in metadata; define truncation metadata and preserve exit status. Add tests with high-volume stdout/stderr.
2. Bound caches/maps in provider models, auth/users, plugins, memory search, delegation, monitor, and session state. Add eviction/TTL tests and metrics for evictions.
3. Audit every `setInterval`, `setTimeout`, `setImmediate`, event-bus subscription, WebSocket, SSE stream, watcher, and pool. Register cleanup with instance/process scope and test disposal leaves no active handles.
4. Harden SSE and WebSocket cleanup in `src/server/server.ts`, `src/server/routes/global.ts`, `src/server/routes/mobile.ts`, `src/server/routes/session.ts`, and PTY routes. Use one cleanup path for normal close, abort, write failure, and transport drop; configure finite idle/request limits instead of unbounded connections.
5. Add soak tests for many reconnecting SSE clients, abandoned clients, long PTY output, repeated workspace sync, and repeated instance disposal.

## Phase 5 — API and Effect architecture convergence

1. Maintain a generated route/support matrix from `src/server/httpapi/bridge.ts`; every route change must update `test/server/httpapi-bridge.test.ts` and regenerate clients where contracts change.
2. Finish the HttpApi bridge in dependency order: JSON routes, auth/security declarations, VCS/remaining session routes, then PTY WebSocket and sync/SSE special cases. Keep Hono as the fallback until parity tests cover status codes, schemas, streaming, auth, and errors.
3. Make route handlers thin adapters: domain services own typed errors; HTTP boundaries map them to declared responses; remove generic error-name guessing as route coverage grows.
4. Continue the Effect migration from `specs/effect/todo.md`: runtime/config flags, global paths, instance context, process/filesystem edges, HTTP client, and bus streams. Migrate one boundary at a time and preserve explicit layers in tests.
5. Do not introduce `effect/unstable/ai` or replace the existing CLI/provider architecture without a separate decision record; use the existing native LLM/AI SDK compatibility plan.

## Phase 6 — Performance, maintainability, and UX quality

1. Replace unbounded/duplicate hot-path work: normalize provider messages in one model-aware pass, cache lowercase search text per operation, avoid repeated deep clones/pretty JSON writes where safe, and window/virtualize large TUI message lists behind flags.
2. Split oversized TUI/session modules only along stable ownership boundaries; preserve behavior with snapshot and interaction tests.
3. Add structured observability for session IDs, request IDs, provider/model, tool IDs, workspace IDs, durations, retries, cancellations, truncation, and resource cleanup without logging secrets or full prompts by default.
4. Replace placeholder scripts in `packages/nikcli/package.json` (`format`, `docs`, `deploy`, `random`) with truthful commands or remove them; ensure `clean` is documented as destructive and not used by CI accidentally.
5. Update stale roadmap/spec references and keep status synchronized with verified implementation, especially `specs/ROADMAP.md`, `specs/effect/*`, and the HttpApi bridge inventory.

## Verification matrix

Run after each phase and before release:

```bash
cd packages/nikcli
bun run typecheck
bun test
bun run lint
bun run build
bun run script/httpapi-bridge-inventory.ts
```

Focused gates:

- Session: `test/session/*`, runner, retry, processor, native runtime, question/permission cancellation.
- Storage/sync: storage, sync, workspace, migration, projection, reconnect/replay/idempotency tests.
- Server: HTTP API bridge, auth, SSE, WebSocket/PTY, mobile/companion, status/error contract tests.
- Tools/security: bash limits, plugin loading, path boundaries, browser/computer permissions, secret redaction.
- Resource safety: active-handle/leak checks, repeated `Instance.disposeAll()`, bounded cache/output tests, long-session soak.
- Release: build binaries for supported targets, smoke `nikcli --help`, `nikcli serve`, a local project session, one streamed prompt, one tool call, cancellation, restart, and workspace restore.

## Rollout and rollback

- Land phases as independently reviewable changes.
- Keep new transport, native provider, virtualization, and resource policies flag-off when behavior changes; expose metrics before defaulting on.
- Roll back by disabling the relevant feature flag or selecting the Hono/legacy provider path; never roll back by deleting persisted data.
- Promote a phase only after focused tests, full suite, build, and a representative soak pass on macOS and Linux (plus Windows build validation).
