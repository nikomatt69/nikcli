# Integrazione autoresearch in nikcli

## Obiettivo

- Portare le idee utili di `karpathy/autoresearch` dentro nikcli senza introdurre un runtime separato: loop autonomo vincolato, charter iniziale, fan-out/fan-in di task, sintesi iterativa, artifact finale leggibile, guardrail forti.
- Farlo in TypeScript/Bun, riusando il piu possibile agenti, tool, delegations, prompt routing e TUI gia presenti.

## Approccio raccomandato

- Aggiungere un subagent nativo `researcher`, read-only e hidden, pensato per raccolta evidenze e sintesi.
- Rendere il lancio **proattivo**: i primary agent (`plan`, `build`, `ralph`) devono poter avviare `task(background=true)` verso `@researcher` quando rilevano un knowledge gap o la necessita di fonti esterne.
- Riutilizzare l'infrastruttura gia pronta di background execution e supervisione: `packages/nikcli/src/tool/task.ts`, `packages/nikcli/src/delegation/manager.ts`, `packages/nikcli/src/tool/delegation.ts`, `packages/nikcli/src/tool/delegator.ts`, `packages/nikcli/src/background/run.ts`.
- Riutilizzare i tool di ricerca gia presenti invece di introdurre subito nuovi tool: `websearch`, `webfetch`, `docs_search`, `docs_request`, `smart_docs`, `memory_search`, `context_collect`, `context_search`, `context_related`, `use_connector`.
- Tenere un eventuale `/research` come alias manuale opzionale in una fase successiva, non come entrypoint principale del primo rollout.

## Perche questa strada

- `autoresearch` qui va tradotto come **workflow** e non come repo separato: nikcli ha gia sessioni, agent registry, delegations, supervisor/delegator, artifact persistenti e routing.
- Un semplice prompt su `@general` sarebbe troppo lasco su permessi, progress tracking e stabilita dell'output.
- Un nuovo orchestration engine sarebbe duplicazione architetturale inutile.
- Il lancio automatico con subagent in background e coerente con il modo in cui nikcli gia lavora: il primary agent continua il lavoro indipendente e incorpora la sintesi appena serve davvero.

## File critici da modificare

  - aggiungere `researcher` come agent nativo `subagent`
  - aggiornare il blocco condiviso dei primary agent per insegnare quando lanciare ricerca autonoma, quando aspettarla e quando continuare senza bloccare il flusso
  - limitare i permessi `task` del researcher a subagent read-only sicuri, senza recursion
- `packages/nikcli/src/tool/task.ts`
  - riconoscere in modo semplice le run di ricerca (`subagent_type === "researcher"`)
  - arricchire metadata e output del background task per una research run
  - migliorare il wake/synthesis loop per summary con findings, fonti e confidence
- `packages/nikcli/src/background/run.ts`
  - estendere `BackgroundRun.Source` o aggiungere metadata minimi per distinguere una research run
  - rendere l'artifact finale piu informativo per le ricerche
- `packages/nikcli/src/delegation/manager.ts`
  - far passare eventuali metadata research-specific dentro il record esistente, senza creare una nuova persistence layer
- `packages/nikcli/src/tool/delegation.ts`
  - esporre meglio status/progress/result per run di ricerca
- `packages/nikcli/src/tool/delegator.ts`

- `packages/nikcli/src/session/prompt.ts`
  - rifiniture minime solo se servono a far convivere bene task normali e task di ricerca nel flusso corrente

## Trigger policy del primary agent

- Lanciare `@researcher` quando almeno una di queste condizioni vale:
  - serve documentazione esterna aggiornata su librerie, API o framework
  - il repo locale non basta per decidere in sicurezza
  - il task richiede confronto tra alternative o raccolta fonti
  - emerge un docs gap o un knowledge gap esplicito
  - e utile continuare lavoro indipendente mentre la ricerca gira in background
- Non lanciare `@researcher` per task banali, refactor locali o richieste puramente meccaniche.
- Consentire una sola research run attiva per parent session finche quella corrente non viene letta o riusata.
- Il researcher non deve mai lanciare un altro `researcher`.

## Contratto del workflow di ricerca

- Trigger: il primary agent rileva che serve una fase di ricerca dedicata.
- Input: messaggio utente corrente + contesto locale + motivo del trigger.
- Il primary agent costruisce un `research charter` compatto con:
  - question
  - scope
  - constraints
  - desired output
  - max rounds
  - max sources
  - prefer-local-first
- Esecuzione: `task(background=true)` verso `@researcher`.
- Fan-out: `@researcher` spezza il tema in 2-4 thread paralleli solo se davvero utile.
- Fan-in: il `delegator` esistente sintetizza i risultati e decide `finalize` o `continue` per 1-2 round aggiuntivi.
- Consumo del risultato: il primary agent usa `delegation` o `delegator` quando raggiunge il punto decisionale dove la ricerca serve davvero, senza bloccarsi all'inizio.
- Output finale: artifact con risposta breve, evidenze chiave, fonti, contraddizioni o unknowns, confidence sintetica.

## Comportamento del nuovo agent `researcher`

- Tool consentiti nel primo rollout:
  - `websearch`, `webfetch`
  - `docs_search`, `docs_request`, `smart_docs`, `docs_context`
  - `memory_search`
  - `context_collect`, `context_search`, `context_related`
  - `read`, `glob`, `grep`
  - `delegation`, `delegator`
  - `task` solo per delegare ad agent read-only (`explore`, `fast-explore`, opzionalmente `planner`)
  - `use_connector` solo per connettori read-only
- Tool negati nel primo rollout:
  - `edit`, `write`, `apply_patch`, `bash`, comandi distruttivi, connettori mutanti
- Policy del researcher:
  - preferire fonti locali e docs gia caricate prima del web generico
  - deduplicare URL e claim
  - legare ogni claim non banale a una fonte
  - dichiarare esplicitamente conflitti o bassa confidenza
  - fermarsi entro budget di round e sorgenti

## Modello dati minimo

- Non creare una nuova collezione Storage dedicata.
- Estendere il record esistente con metadata piccoli e coerenti, ad esempio:
  - `kind: "research"`
  - `question`
  - `sourceCount`
  - `followUpRounds`
  - `confidence`
  - `finalStatus`
- Dove possibile, dedurre il tipo di run direttamente da `agent === "researcher"` per ridurre cambi strutturali.

## Fasi implementative

### Fase 1 - Core architecture

- aggiungere `researcher` in `packages/nikcli/src/agent/agent.ts`
- insegnare ai primary agent a lanciare `@researcher` in autonomia in background quando scattano i trigger
- costruire il `research charter` direttamente nel payload del task
- taggare/metadatizzare la research run in `task.ts` + `background/run.ts`
- mantenere il workflow completamente read-only

### Fase 2 - Summaries e UX

- migliorare `delegation`/`delegator` per summary research-aware
- far emergere source count, round count e confidence nel progresso TUI
- rifinire il formato dell'artifact finale per renderlo piu leggibile e utile al primary agent

### Fase 3 - Manual escape hatch e consolidamento

- aggiungere opzionalmente `/research` come alias manuale per utenti power e debug
- aggiungere un'azione esplicita opt-in per salvare risultati o fonti utili nella docs library
- valutare un tool dedicato solo se prompt + task + delegator non bastano piu

## Verifica end-to-end

- `bun run typecheck`
- `bun test` oppure test mirati sui moduli toccati
- verifica manuale proattiva: prompt che richiede documentazione esterna o confronto architetturale, e controllo che il primary agent lanci `@researcher` in bg da solo
- verifica manuale TUI:
  - partenza background run
  - aggiornamenti progress/delegation
  - artifact finale leggibile
  - `delegator summarize` utile e sintetico
  - cancel/read/summarize funzionanti
- verifica architetturale:
  - i permessi del nuovo agent restano read-only
  - nessuna recursion `researcher -> researcher`
  - una sola research run attiva per parent session
  - SDK rigenerato solo se cambia davvero la surface server/API

## Decisione finale

- Integrare `autoresearch` in nikcli come **subagent specifico `researcher` che parte autonomamente in background**, non come repo separato e non come semplice slash command manuale.
- Questa e la soluzione piu coerente con la tua architettura attuale, con il minimo numero di file nuovi e il massimo riuso dell'infrastruttura gia esistente.
