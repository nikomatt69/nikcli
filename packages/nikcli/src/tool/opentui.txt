Render a rich, enterprise-grade terminal dashboard in the TUI dialog panel.

Use this tool whenever the user would benefit from *seeing* structured information rather than reading prose. It is the right call for: performance reports, status dashboards, incident summaries, deployment overviews, code review digests, benchmark comparisons, project KPIs, system health rollups, multi-environment status grids, time-series trends, distributions, taxonomies/hierarchies, configuration audits, and explanatory documents that mix code, tables, and diagrams.

> **CRITICAL**: If you need to show a *structural diagram*, a *flow*, a *status board*, an *architecture overview*, a *pipeline*, or any other visual layout — call this tool. **Do not draw ASCII-art diagrams in prose.** The chat-stream markdown renderer cannot color or align hand-drawn box-drawing characters reliably. Use `tree` for hierarchies, `timeline` for pipelines, `status_grid` for fleet maps, `section`+`grid` for arrangement, and the chart components for data.

---

## Authoring principles

1. **Pick the component that *answers the question*, not the prettiest one.** A user asking "is the deploy healthy?" wants a `status_grid` or a `stat_grid` with deltas — not a bar chart of node counts.
2. **Group related information.** Use `section` to title and describe a logical block; use `grid` to lay multiple compact components side-by-side. A dashboard with 6 cohesive components beats 12 scattered ones.
3. **Set context with units and deltas.** Numbers without `unit`, `format`, `delta`, or `trend` are easy to misread. For `stat`, always supply at least one of those when the underlying metric is dynamic.
4. **Color by *semantics*, not aesthetics.** Use `success`/`warning`/`error`/`info` to convey state. Reserve `primary`/`accent` for emphasis.
5. **Keep labels short.** Under ~20 characters for chart axes, status grids, and table headers — terminals are narrow.
6. **Never invent data.** If a metric is unknown, omit it or surface it as `pending` — never fabricate a value.

## Component catalogue

### Foundational

- `text` — Styled paragraph. Use `style` for semantic tinting (`info`/`success`/`warning`/`error`/`muted`) or `code` for a monospace block. For longer prose with formatting, prefer `markdown`.
- `markdown` — Full GitHub-flavored markdown: headings, lists, **bold**, *italic*, `code`, fenced blocks with syntax highlighting (via filetype tag), and tables with real borders. Use for explanations, runbooks, summaries with mixed content.
- `code` — Syntax-highlighted code block. Supply `filetype` (`ts`, `tsx`, `bash`, `python`, `json`, `yaml`, `sql`, etc.). Set `showLineNumbers: true` for code review contexts.
- `diff` — Unified or split diff with proper +/− coloring. Use for code review, config drift, before/after comparisons.
- `alert` — Boxed callout with severity icon. Use sparingly for things the user must notice (incident, breaking change, action required).

### Data display

- `table` — Headers + rows + optional `totals` row. Use `align` (`left`/`center`/`right` per column) for numeric data. Use `rowColors` to flag attention-worthy rows (`error`/`warning`/`success`/`muted`).
- `key_value` — Label : Value pairs. Use `status` per item to tint values. Group with `group` field for sections of related keys (e.g. "Build", "Runtime", "Network").
- `tree` — Hierarchical view: file trees, dependency graphs, org charts. Each node may carry a `value` (right-aligned suffix) and a `status`. Up to 4 levels of nesting.

### Statistics

- `stat` — A single KPI card: big number + label + optional `delta` + `trend` (`up`/`down`/`flat`) + optional inline `sparkline`. Set `format` (`plain`/`compact`/`currency`/`percent`/`bytes`/`duration`) to render the value correctly. Prefer this over a one-row table for "the number that matters".
- `stat_grid` — A row of KPI cards. The dashboard hero. Default 3–4 stats per row; auto-wraps on narrow terminals. Use for "top of the page" summaries.

### Charts

- `bar_chart` — Categorical comparison. `orientation: "horizontal"` (default, best for many labeled categories) or `"vertical"` (good for time buckets). Set `showValues` and/or `showPercentages` for annotated bars. Per-item `color` overrides the default.
- `line_chart` — Time-series or sequential numeric data. Multi-series with named, colored lines. Provide `labels` for x-axis ticks (sparse is fine). Set `height` (rows) to control vertical resolution.
- `histogram` — Distribution over named bins. Use when the user cares about shape (skew, modes, outliers), not exact values.
- `heatmap` — Matrix of values colored by intensity. `colorScale: "mono"` (single hue), `"diverge"` (negative/zero/positive), or `"traffic"` (green→yellow→red). Use for service × environment dashboards or co-occurrence matrices.
- `gauge` — Single-value indicator against a max, with optional colored `thresholds`. Use for "how close to limit" semantics (quota, latency budget, error rate vs SLO).
- `progress_bars` — A list of fill-bars. Each row has `value`/`max`/`unit`. Optional `thresholds` color the bar at breakpoints. Use for parallel quotas or task completion.

### Process & state

- `timeline` — Ordered events with `status` icons (`done` ✓ / `active` ● / `pending` ○ / `error` ✗ / `skipped` ∅). Optional `duration` shows how long each step took. Use for pipelines, incident timelines, deploys.
- `status_grid` — A grid of cells, each `label` + `status` + optional `detail`. Use for "fleet at a glance": services × environments, regions, agents.

### Layout

- `section` — A titled container with optional `description`. Wrap a coherent set of components in it.
- `grid` — Multi-column container. Set `columns` (1–4) or omit to auto-pick based on terminal width. Use to lay 2–4 compact stats/charts side-by-side.

`section` and `grid` accept any non-container component as children. They can be combined: e.g. a top-level layout of multiple `section`s, each containing a `grid` of `stat`s and a `line_chart`.

---

## Color tokens

Pass `color` (where supported) using semantic tokens — they resolve against the user's active theme:

- `primary`, `secondary`, `accent` — brand / emphasis
- `success`, `warning`, `error`, `info` — semantic state
- `muted` — de-emphasized
- `default` — body text color

Avoid hardcoded hex colors. They will not adapt to the user's light/dark theme.

## Composition cheatsheet

| Goal                                       | Component(s) of choice                                 |
|--------------------------------------------|---------------------------------------------------------|
| "One number that matters"                  | `stat`                                                 |
| Top-of-dashboard summary (3–6 KPIs)        | `stat_grid` (deltas + sparklines)                      |
| Time-series / sequential trend             | `line_chart` (multi-series)                             |
| Compare categories                         | `bar_chart` (horizontal for ≥4, vertical for ≤6 time)  |
| Distribution shape                         | `histogram`                                            |
| Matrix view (service × env)                | `heatmap` or `status_grid`                              |
| Quota / utilization                        | `gauge` (single) or `progress_bars` (parallel)         |
| Step-by-step state (build, deploy, INC)    | `timeline`                                             |
| Hierarchy (deps, files, taxonomy)          | `tree`                                                 |
| Tabular data                               | `table` (use `align`, `rowColors`, `totals`)            |
| Config / status fields                     | `key_value` (with `group`)                              |
| Code review                                | `table` (files) + `diff` + `markdown` (notes)          |
| Long-form explanation                      | `markdown` (lists, code, sub-tables)                    |
| Code snippet                               | `code` (set `filetype`, optionally `showLineNumbers`)   |
| Big urgent message                         | `alert` (sparingly)                                    |
| Side-by-side compact views                 | `grid` (2–4 children)                                  |
| Titled logical block                       | `section` (with `description` if context is needed)    |

## Limits & defaults

- Top-level: 1–30 components. The dialog shows tabs when there are 2+; keys 1–9 jump to tabs 1–9, **0** jumps to tab 10; use tab/shift+tab for tabs 11–30.
- `bar_chart.barWidth` / `progress_bars.barWidth`: 10–60 chars. Default 40.
- `line_chart.height`: 4–20 rows. Default 8. `line_chart.series`: 1–6.
- `stat_grid.columns` / `grid.columns`: 1–4. Default auto (3–4 on wide terminals, 2 on narrow, 1 on tight).
- `heatmap`: up to ~20 rows × ~20 cols recommended.
- `tree`: up to 4 levels of nesting.
- `timeline`: up to ~30 events comfortably.
- All numeric values are validated; out-of-range inputs are rejected by the schema.

---

## Interactivity available to the user

The rendered dialog supports, automatically:

- **j / k / ↑ / ↓** — scroll content
- **tab / shift+tab** — next / previous component when there are 2+ top-level components
- **1 – 9** — jump to tabs 1–9; **0** — jump to tab 10; **tab / shift+tab** — all tabs (including 11–30)
- **e** — export the visualization as markdown to the clipboard
- **?** — toggle keybind help
- **esc** — close the dialog

You do not need to instruct the user about these — they are surfaced in the dialog footer.

## Robust calling patterns (learned from real-world testing)

Some JSON shapes are fragile when round-tripped through the tool-call parser. The patterns below are guaranteed to render reliably; prefer them when in doubt.

### Prefer `grid` + `children` over direct-array components

Array-of-object fields with these names are sometimes received by the schema validator as a plain object instead of an array, even when the JSON you emit is correct:

| Fragile array field | Affected component | Safe replacement |
|---|---|---|
| `items` | `stat_grid`, `bar_chart`, `progress_bars`, `key_value`, `status_grid` | `grid` of `stat` / `text` / `markdown` cells |
| `nodes` | `tree` | `markdown` with ASCII / fenced `text` block, or `code` (filetype `text`) |
| `series` | `line_chart` | `markdown` with table + sparkline-styled `stat` row |
| `events` | `timeline` | `code` (filetype `text`) with an ASCII timeline |
| `bins` | `histogram` | `bar_chart` (but also uses `items` — fall back to `markdown` table) |
| `rowLabels` · `colLabels` · `values` | `heatmap` | `markdown` table with status-colored cells |
| `headers` · `rows` | `table` | `markdown` table — it renders with real borders anyway |
| `rowColors` · `align` · `totals` | `table` extras | not used in the safe `markdown` path |

**Safe rule**: any time you would reach for a component whose array payload uses one of the names above, reach for `grid` + `children` (or `markdown`) instead. The `grid` component is verified to receive its `children` array correctly and renders `stat` cards in a clean KPI row.

### `section` and nested `grid`

The schema **allows** `section > grid > stat` (and other leaf children inside the grid). `SafeVizSpecZod` unwraps `{item:…}` envelopes through that tree.

Some **tool-call parsers** still break on deeply nested or wrapped `section > grid` payloads. If validation fails:

- Prefer **`grid` as a top-level** tab (sibling of `section` / `alert`) for KPI rows.
- Or keep **`section` children** to leaves only: `text`, `markdown`, `code`, `alert`.

When nesting works, use it to group a titled block with a multi-column layout inside one tab.

### `section` shape

`section` accepts `title` (optional) and `children` (required, 1–30 items). Each child may be any **leaf** component or a **`grid`** (not another `section`). Do **not** add a `description` field at the section level — the runtime treats it as unrecognized even though the static schema permits it. If you need a description, fold it into the first `markdown` child instead.

### `alert` shape

`alert` only takes `severity` (`info` / `success` / `warning` / `error`), `title` (optional), and `message` (required). No extra keys.

### Flat is better than deep

Prefer this structure for multi-tab dashboards (up to **30** top-level components):

```jsonc
{
  "title": "...",
  "components": [
    { "type": "alert", "severity": "info",   "title": "...", "message": "..." },
    { "type": "section", "title": "1 · ...",  "children": [{ "type": "markdown", "content": "..." }] },
    { "type": "section", "title": "2 · ...",  "children": [{ "type": "code", "filetype": "text", "content": "..." }] },
    { "type": "section", "title": "3 · ...",  "children": [{ "type": "markdown", "content": "..." }] },
    { "type": "alert", "severity": "success", "title": "...", "message": "..." }
  ]
}
```

One `markdown` or `code` child per `section` keeps the validator happy and the dashboard scannable. Reach for 2 children only when you genuinely need a callout (`alert`) **after** a body of text inside the same logical block.

### Component-to-replacement cheat sheet

| You want | Robust path |
|---|---|
| KPI hero (5–8 numbers) | top-level `grid` of `stat` |
| KPI block under a titled section | `section` with one `grid` child of `stat`s (schema-valid; fallback to top-level `grid` if parser rejects) |
| Grouped KPIs by category | sibling `section`s, each with one `markdown` table inside |
| Status fleet board | `markdown` with status icons (✓ ⚠ ✗ ℹ) in a table |
| Hierarchy / dependency graph | `code` (filetype `text`) with a fenced ASCII tree |
| Process / pipeline timeline | `code` (filetype `text`) with ASCII timeline |
| Tabular data | `markdown` with a real-bordered table |
| Single-callout block | `section` with a `markdown` child (or top-level `alert`) |
| Multi-callout block | top-level `alert`s or `section` of `markdown` |

### When you *must* use a fragile component

If the task genuinely calls for `tree` (e.g. user asked for a navigable hierarchy) or `timeline` (long sequenced events) and the runtime rejects the call:

1. Retry once with a smaller payload (≤ 4 items, 2 levels deep for `tree`).
2. If it still fails, fall back to `markdown` + `code` (filetype `text`) — the user gets the same information rendered as a text block.

These patterns are the minimum-surprise path. The full catalogue above is correct for the schema; the patterns above are correct for the **tool-call parser** that sits between you and the schema.

## When NOT to use this tool

- For a single sentence answer — just respond in prose.
- For interactive workflows that need input — this is read-only display, not a form.
- For data you have not actually computed — never synthesize numbers to fill a chart.
- When the user explicitly asks for plain text or JSON output.
- For trivial 2-row, 1-column information — a plain markdown answer is faster.
